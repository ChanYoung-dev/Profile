CHAPTER 05

Deep Dive · Engineering Stories

Why · How · Impact

4가지 핵심 엔지니어링 의사결정의 상세 기록입니다. 문제의 맥락, 선택한 접근, 그리고 결과까지를 한 페이지에 정리했습니다.

STORY 01 · MESSAGING RabbitMQ 도입 — 주문 트랜잭션과 외부 API의 분리
Problem
주문 완료 후 현금영수증 발급을 동기식으로 처리하면서 발생하던 외부 API 지연으로 인한 응답 지연, 장애 전파, 컨테이너 재기동 시 메시지 유실 문제를 해결하였습니다.
Constraint
현금영수증 발급은 외부 제휴 API에 의존하며 응답이 1분 이상 지연되는 경우가 있었습니다. 주문 API 스레드 장시간 점유 → 트래픽 증가 시 스레드 풀 고갈 위험. 발급 실패 시 주문 트랜잭션까지 롤백되는 구조로 과도한 결합. MSA 환경에서 컨테이너 재기동 시 강제 종료로 인한 메시지 유실 가능성이 있었습니다.
Decision
  • DLX + TTL 기반 retry 구조 설계 — 외부 API 실패 시 자동 재처리
  • RabbitMQ exclusive consumer — 다중 Consumer 환경에서도 주문 단위 순서 보장
  • Docker 실행 방식을 exec로 변경 — SIGTERM이 Spring lifecycle까지 전달
  • graceful shutdown 정상 동작 보장 — MQ · 애플리케이션 · 인프라(Nomad/Consul)까지 고려한 설계
Outcome
주문 API 응답 시간이 외부 API 지연과 분리되어 개선되었고, 현금영수증 발급 실패가 주문 실패로 이어지지 않게 되었습니다. 컨테이너 재기동 상황에서도 메시지 유실 없이 안정적으로 처리되며, 재시도 및 DLQ 기반의 자동 복구 가능한 고가용성 구조를 구축했습니다.
STORY 02 · QUALITY 통합 테스트 환경 구축 — Testcontainers 기반 격리 환경
Problem
주문 도메인에서 기능 수정 및 정책 변경 시 발생하는 사이드 이펙트를 해결하기 위해 테스트 코드를 도입했습니다.
Constraint
주문 도메인은 결제 · 배송 · 쿠폰 · 포인트 등 여러 도메인이 얽혀 있어 작은 변경에도 장애 위험이 있었습니다. 또한 MSA 환경에서:
  • 개발 DB 사용 시 외부 트래픽으로 인한 테스트 환경 오염
  • 분산 트랜잭션 구조에서 테스트 후 데이터 롤백 어려움
  • 서비스 간 DB 공유로 인한 테스트 간 의존성
  • 외부 서비스 경계가 불명확해 테스트 범위가 모호
Decision
Testcontainers를 도입해 실제 DB 환경을 컨테이너로 구성하여 외부 환경과 완전히 분리된 격리 테스트 환경을 구축했습니다. 서비스 간 책임 경계를 재정의하여 주문 API에서 수행해야 할 로직을 명확히 분리하고, 외부 API(포인트 등)는 mock 처리하도록 개선했습니다. 포인트 API의 데이터 흐름을 분석해 주문 도메인에 속하는 비즈니스 로직을 주문 API로 재배치하여 각 서비스가 자신의 책임에 맞는 역할만 수행하도록 구조를 재설계했습니다.
Outcome
테스트의 재현성과 신뢰성이 크게 향상되었으며, 기능 변경 시 사이드 이펙트를 사전에 검증할 수 있게 되었습니다. 수동 검증 의존에서 벗어나 개발 생산성과 코드 안정성이 함께 개선되었습니다.

STORY 03 · SECURITY MSA에서의 XSS 처리 대응 — 전사 공통 기준 수립
Problem
MSA 환경에서 서비스별로 상이하게 적용되던 XSS 대응 방식으로 발생한 이중 이스케이프 · 데이터 변형 · JSON 파싱 오류를 해결했습니다.
Constraint
각 서비스마다 필터 · 인터셉터 · 화면단 등 서로 다른 위치에서 XSS 처리를 수행하면서, 동일 데이터가 여러 API를 거치는 과정에서 중복 이스케이프가 발생했습니다. 데이터 변형 및 비정상 노출이 발생하였고, MSA 구조 특성상 여러 서비스를 동시에 고려해야 해 영향 범위가 넓고 검증이 어려운 제약이 있었습니다.
Decision
개별 이슈 대응이 아닌 전사 공통 XSS 처리 기준 수립으로 접근했습니다. 정보보안 부서와 협업해 정책을 정의하고, 애노테이션 기반 공통 처리 구조를 설계해 전사 가이드로 정리·배포하고 적용을 주도했습니다. 기존 데이터 흐름을 분석해 중복 처리 및 데이터 변형 발생 구간을 식별하고, 서비스 전반에 걸쳐 일관된 방식으로 정비했습니다.
Outcome
서비스 간 XSS 처리 방식이 일관되게 정리되어 데이터 변형 및 이중 처리 문제가 해소되었습니다. 전사 가이드 적용으로 조직 전반의 보안 수준이 향상되었으며, ISMS 점검에서 XSS 관련 지적 건수가 크게 감소하는 성과를 달성했습니다.
STORY 04 · DESIGN OOP 리팩토링 — 결제 도메인의 전략 패턴 적용
Problem
주문 결제 도메인에서 다양한 결제 수단(카드 · 포인트 · 간편결제 등)과 복합 결제를 처리하면서 발생하던 if-else 기반 분기 로직 증가 및 변경 시 사이드 이펙트 문제를 해결했습니다.
Constraint
결제 도메인은 정책 변경과 신규 결제 수단 추가가 빈번한 영역으로, 기존 구조에서는 기능이 추가될 때마다 조건문이 계속 증가하고 기존 코드를 수정해야 했습니다. 변경 범위가 넓어지고 작은 수정에도 예상치 못한 오류가 발생할 수 있는 구조로, 유지보수성과 확장성이 크게 저하된 상태였습니다.
Decision
조건문을 줄이는 것이 아니라 변경의 책임을 객체로 분리하는 방향으로 접근했습니다.
  • 결제 방식을 객체로 추상화 후 전략 패턴(Strategy Pattern) 도입
  • 각 결제 수단이 자신의 행위를 스스로 처리하도록 설계
  • 결제 방식 선택 로직을 팩토리로 캡슐화
  • 클라이언트 코드가 구체 구현이 아닌 추상화에 의존하도록 개선
Outcome
조건문 중심의 절차적 구조에서 벗어나 다형성 기반의 객체지향 구조로 개선되어, 결제 로직의 확장성과 유지보수성이 크게 향상되었습니다. 정책 변경이나 신규 결제 수단 추가 시 기존 코드를 수정하지 않고 확장할 수 있는 OCP 만족 구조를 확보했습니다.
