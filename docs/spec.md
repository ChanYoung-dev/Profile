# 1.Rabbit MQ 도입
## 어떤 문제를 해결했는지
주문 완료 후 현금영수증 발급을 동기식으로 처리하면서 발생하던 외부 API 지연으로 인한 응답 지연, 장애 전파, 컨테이너 재기동 시 메시지 유실 문제를 해결하였습니다.

## 그 문제가 왜 중요했고 어떤 제약이 있었는지
현금영수증 발급은 외부 제휴 API에 의존하며, 실제로 응답이 1분 이상 지연되는 경우가 있었습니다. 이로 인해 주문 API 스레드가 장시간 점유되어 트래픽 증가 시 전체 서비스 지연 및 스레드 풀 고갈 위험이 있었습니다.
또한 발급 실패 시 주문 트랜잭션까지 롤백되는 구조로, 비즈니스 중요도에 비해 과도하게 결합되어 장애 전파가 발생하는 문제가 있었습니다.
추가로 MSA 환경에서 컨테이너 재기동 시 헬스체크 지연 및 강제 종료로 인해 메시지 처리 중 유실이 발생할 수 있는 문제가 있었습니다.

## 그 과정에서 어떤 역할을 맡았고 어떤 판단을 했는지
현금영수증 발급을 주문 트랜잭션에서 분리하기 위해 RabbitMQ 기반 비동기 처리 구조로 전환하였습니다.
단순 비동기 처리에 그치지 않고,
- DLX + TTL 기반 retry 구조를 설계하여 외부 API 실패 시 자동 재처리
- RabbitMQ exclusive consumer를 적용하여 다중 Consumer 환경에서도 주문 단위 순서 보장
  하도록 설계하였습니다.

또한 컨테이너 재기동 시 메시지 처리 중 유실되는 문제를 해결하기 위해 Docker 실행 방식을 exec로 변경하여 SIGTERM이 Spring lifecycle까지 전달되도록 개선하고, graceful shutdown이 정상적으로 동작하도록 구성하였습니다. 이를 통해 MQ, 애플리케이션, 인프라(Nomad/Consul)까지 고려한 안정적인 처리 구조를 설계할 수 있었습니다.

## 결과적으로 어떤 변화가 있었는지
주문 API 응답 시간이 외부 API 지연과 분리되어 개선되었고, 현금영수증 발급 실패가 주문 실패로 이어지지 않도록 구조가 개선되었습니다. 또한 컨테이너 재기동 상황에서도 메시지 유실 없이 안정적으로 처리되었으며, 재시도 및 DLQ 기반으로 장애 발생 시 자동 복구가 가능한 구조를 구축하였습니다.
그 결과 주문 도메인의 정합성과 시스템 전반의 신뢰성이 크게 향상되고 고가용성 시스템을 개발할 수 있게 되었습니다.


# 2.통합 테스트 환경구축
## 어떤 문제를 해결했는지
주문 도메인에서 기능 수정 및 정책 변경 시 발생하는 사이드 이펙트를 해결하기 위해 테스트 코드를 도입하였습니다.

## 그 문제가 왜 중요했고 어떤 제약이 있었는지
주문 도메인은 결제, 배송, 쿠폰, 포인트 등 여러 도메인이 복잡하게 얽혀 있어 작은 변경에도 예상치 못한 장애가 발생할 수 있었습니다.
기존에는 수동 검증에 의존하고 있어 테스트 범위가 넓고 비효율적이었으며, 변경에 대한 안정성을 보장하기 어려운 상황이었습니다.

또한 MSA 환경에서 통합 테스트를 수행하는 과정에서 다음과 같은 제약이 있었습니다.

- 개발 DB를 사용할 경우 외부 트래픽에 의해 테스트 결과가 변하는 테스트 환경 오염 문제
- 분산 트랜잭션 구조에서 테스트 후 데이터 롤백이 어려운 문제
- 서비스 간 API 호출 시 DB를 공유하는 구조로 인해 테스트 간 의존성 발생
- 외부 서비스(Mock 처리 대상)의 경계가 불명확하여 테스트 범위가 모호한 문제

## 그 과정에서 어떤 역할을 맡았고 어떤 판단을 했는지
Testcontainers를 도입하여 테스트 실행 시 실제 DB 환경을 컨테이너로 구성하고, 외부 환경과 완전히 분리된 격리된 테스트 환경을 구축하였습니다. 또한 서비스 간 책임 경계를 재정의하여, 주문 API에서 수행해야 할 로직을 명확히 분리하고 외부 API(포인트 등)는 mock 처리하도록 개선하였습니다. 이 과정에서 포인트 API의 기능과 데이터 흐름을 분석하여, 주문 도메인에 속하는 비즈니스 로직이 외부 서비스에 분산되어 있음을 확인하였습니다. 이에 따라 해당 로직을 주문 API로 재배치하고, 각 서비스가 자신의 책임에 맞는 역할만 수행하도록 구조를 재설계하였습니다.
이를 통해 테스트 대상 범위를 명확히 하고, 테스트 실행 시 외부 시스템이나 데이터에 영향을 받지 않도록 설계하였습니다.

## 결과적으로 어떤 변화가 있었는지
테스트의 재현성과 신뢰성이 크게 향상되었으며, 기능 변경 시 사이드 이펙트를 사전에 검증할 수 있게 되었습니다.
또한 수동 검증에 의존하던 방식에서 벗어나 개발 생산성과 코드 안정성이 함께 개선되었습니다.





# 3.MSA에서의 XSS 처리 대응
## 어떤 문제를 해결했는지
MSA 환경에서 서비스별로 상이하게 적용되던 XSS 대응 방식으로 인해 발생한 이중 이스케이프, 데이터 변형, JSON 파싱 오류 문제를 해결하였습니다.

## 그 문제가 왜 중요했고 어떤 제약이 있었는지
각 서비스마다 필터, 인터셉터, 화면단 등 서로 다른 위치에서 XSS 처리를 수행하면서, 동일 데이터가 여러 API를 거치는 과정에서 중복 이스케이프가 발생하는 문제가 있었습니다. 이로 인해 데이터 변형 및 일부 화면에서의 비정상 노출이 발생하였고, MSA 구조 특성상 여러 서비스를 동시에 고려해야 하기 때문에 영향 범위가 넓고 검증이 어려운 제약이 있었습니다.

## 그 과정에서 어떤 역할을 맡았고 어떤 판단을 했는지
개별 이슈 대응이 아닌 전사 공통 XSS 처리 기준을 수립하는 방향으로 접근하였습니다. 정보보안 부서와 협업하여 정책을 정의하고, 애노테이션 기반의 공통 처리 구조를 설계한 뒤 이를 전사 가이드로 정리하여 배포하고 적용을 주도하였고, 또한 기존 데이터 흐름을 분석하여 중복 처리 및 데이터 변형이 발생하는 구간을 식별하고 서비스 전반에 걸쳐 일관된 방식으로 개선이 이루어지도록 주도적으로 정비하였습니다.

## 결과적으로 어떤 변화가 있었는지
서비스 간 XSS 처리 방식이 일관되게 정리되었고, 데이터 변형 및 이중 처리 문제가 해소될수 있었습니다. 또한 전사 가이드 적용을 통해 조직 전반의 보안 수준이 향상되었으며, ISMS 점검에서 XSS 관련 지적 건수가 크게 감소하는 성과를 달성하였습니다.

# 4.OOP 리팩토링
## 어떤 문제를 해결했는지
주문 결제 도메인에서 다양한 결제 수단(카드, 포인트, 간편결제 등)과 복합 결제를 처리하는 과정에서 발생하던 if-else 기반 분기 로직 증가 및 변경 시 사이드 이펙트 문제를 해결하였습니다.

## 그 문제가 왜 중요했고 어떤 제약이 있었는지
결제 도메인은 정책 변경과 신규 결제 수단 추가가 빈번한 영역으로, 기존 구조에서는 기능이 추가될 때마다 조건문이 계속 증가하고 기존 코드를 수정해야 하는 문제가 있었습니다. 이로 인해 변경 범위가 넓어지고, 작은 수정에도 예상치 못한 오류가 발생할 수 있는 구조였으며, 유지보수성과 확장성이 크게 저하된 상태였습니다.

## 그 과정에서 어떤 역할을 맡았고 어떤 판단을 했는지
단순히 조건문을 줄이는 것이 아니라, 변경의 책임을 객체로 분리하는 방향으로 구조 개선을 진행하였습니다. 결제 방식을 객체로 추상화하고, 전략 패턴을 도입하여 각 결제 수단이 자신의 행위를 스스로 처리하도록 설계하였습니다. 또한 결제 방식 선택 로직을 팩토리로 캡슐화하여, 클라이언트 코드가 구체 구현이 아닌 추상화에 의존하도록 개선하였습니다.

## 결과적으로 어떤 변화가 있었는지
조건문 중심의 절차적 구조에서 벗어나 다형성을 기반으로 한 객체지향 구조로 개선되었으며, 결제 로직의 확장성과 유지보수성이 크게 향상되었습니다. 또한 변경에 따른 사이드 이펙트가 감소하고, 안정적인 기능 확장이 가능한 구조를 확보하였으며 이를 통해 정책 변경이나 신규 결제 수단 추가 시 기존 코드를 수정하지 않고 확장할 수 있었습니다.
