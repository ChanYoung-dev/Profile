# 베네피아 현금영수증 벤더별 발행 구조 정리

## 1. 문서 목적

베네피아의 기존 현금영수증 발급 구조와 토스페이먼츠 전환 이후 벤더사별 현금영수증 발급 구조를 정리한다.

주요 대상은 다음과 같다.

- 현금영수증 기본 개념
- 과세·면세·복합 과세 처리
- 복지포인트의 현금영수증 대상 여부
- 위탁판매 및 위탁계약발행의 의미
- 기존 NXmile 발급 구조
- 토스페이먼츠 `businessNumber`를 이용한 벤더별 발행
- 주문번호 및 원장 설계
- 취소·부분취소 처리 시 고려사항

---

## 2. 현금영수증 기본 개념

현금영수증은 구매자가 상품 또는 서비스 대금을 현금성 결제수단으로 지급했을 때, 해당 거래를 국세청에 신고하기 위한 증빙이다.

현금은 지폐만 의미하지 않는다. 일반적으로 다음과 같은 결제수단이 포함될 수 있다.

- 계좌이체
- 가상계좌
- 무통장입금
- 현금성 간편결제
- 현금으로 충전한 선불전자지급수단

반면 다음 항목은 일반적으로 현금영수증 발급 대상이 아니다.

- 신용카드 결제금액
- 체크카드 결제금액
- 신용카드 기반 간편결제
- 일반 적립포인트 사용액
- 쿠폰 또는 할인금액

카드 결제는 카드매출전표가 별도의 증빙 역할을 하므로 같은 금액에 현금영수증을 중복 발급하지 않는다.

---

## 3. 복지포인트와 현금영수증

### 3.1 회사가 지급한 복지포인트

회사가 직원에게 무상으로 지급한 일반적인 복지포인트는 직원이 자신의 현금을 지급한 것이 아니므로, 원칙적으로 직원 명의 현금영수증 발급 대상이 아닌 것으로 본다.

예시:

```text
상품금액: 100,000원
회사 지급 복지포인트: 100,000원
직원 실제 현금 부담액: 0원
```

이 경우 일반적으로 현금영수증 발급 대상 금액은 0원이다.

### 3.2 복지포인트와 현금성 결제의 혼합

```text
상품금액: 100,000원
회사 지급 복지포인트: 70,000원
계좌이체: 30,000원
```

일반적인 처리 방향:

```text
현금영수증 발급 대상: 30,000원
복지포인트 사용액: 발급 대상 제외
```

추가 결제금액을 카드로 결제했다면 현금영수증이 아니라 카드전표가 발급된다.

### 3.3 고객이 직접 충전한 포인트

고객이 자신의 계좌나 현금으로 충전한 포인트라면 선불전자지급수단에 해당할 가능성이 있다. 이 경우에는 충전 시점이 아니라 실제 상품 구매 시점에 현금영수증 대상이 될 수 있다.

다만 베네피아 포인트의 법적·회계적 성격에 따라 달라질 수 있으므로 다음을 확인해야 한다.

- 회사가 지급한 복지포인트인지
- 고객이 직접 충전한 포인트인지
- 할인수단인지
- 결제수단인지
- 정산 시 실제 현금으로 취급되는지

## 4. 토스페이먼츠 현금영수증 금액 구조

현금영수증 발급 요청의 주요 금액 파라미터는 다음과 같다.

- `amount`: 현금영수증의 전체 발급금액
- `taxFreeAmount`: 전체 발급금액 중 면세 금액

즉, 전체 현금영수증 발급금액은 `amount`이다.

`taxFreeAmount`는 추가 발급금액이 아니며, `amount` 안에서 면세로 구분되는 부분이다.

### 4.1 전액 과세

```json
{
  "amount": 10000,
  "taxFreeAmount": 0
}
```

의미:

```text
현금영수증 총 발급액: 10,000원
면세 금액: 0원
과세 대상 금액: 10,000원
```

### 4.2 과세·면세 혼합

```json
{
  "amount": 10000,
  "taxFreeAmount": 3000
}
```

의미:

```text
현금영수증 총 발급액: 10,000원
면세 금액: 3,000원
과세 대상 금액: 7,000원
```

과세 대상 금액 7,000원은 공급가액과 부가가치세로 다시 나뉜다.

```text
부가가치세 = (amount - taxFreeAmount) / 11
```

따라서 문서의 “보낸 금액만큼 현금영수증이 발급됩니다”라는 표현은 다음 의미로 이해해야 한다.

> 전체 현금영수증은 `amount`만큼 발급되고, `taxFreeAmount`만큼은 면세 금액으로 구분된다.

## 5. 토스페이먼츠 상점의 의미

토스페이먼츠 문서에서 말하는 상점은 일반적으로 개별 벤더사가 아니라, 토스페이먼츠와 계약하고 MID 또는 인증키를 보유한 결제 주체를 의미한다.

베네피아가 토스페이먼츠와 계약하고 결제 및 정산의 주체가 된다면 기본적인 상점은 베네피아이다.

```text
구매자
  ↓
베네피아
  ↓
토스페이먼츠
  ↓
베네피아 정산
  ↓
벤더사 정산
```

다만 현금영수증 발행 사업자는 토스페이먼츠의 별도 `businessNumber` 파라미터를 통해 벤더사 사업자번호로 지정할 수 있다.

## 6. 위탁판매의 의미

위탁판매는 벤더사가 자신의 상품 판매를 베네피아에 맡기고, 베네피아가 주문·결제·판매 채널을 대신 제공하는 구조다.

### 6.1 매입판매

```text
벤더사 → 베네피아에 상품 납품
베네피아 → 고객에게 재판매
```

일반적인 구조:

- 고객 대상 판매자: 베네피아
- 고객 대상 매출: 베네피아
- 현금영수증 발행자: 베네피아
- 벤더사: 베네피아의 상품 공급처

### 6.2 위탁판매

```text
벤더사 상품
  ↓
베네피아가 판매를 대행
  ↓
고객 구매
```

일반적인 구조:

- 실제 상품 공급자: 벤더사
- 판매 채널 제공자: 베네피아
- 상품 매출 귀속자: 계약에 따라 벤더사
- 베네피아 수익: 판매수수료
- 현금영수증 발행자: 계약에 따라 벤더사

예시:

```text
고객 결제금액: 100,000원
베네피아 판매수수료: 10,000원
벤더사 정산금: 90,000원
```

위탁판매에서는 상품 판매액 100,000원이 벤더사 매출로 귀속되고, 베네피아는 수수료 10,000원을 자신의 수익으로 인식하는 구조가 가능하다.

## 7. 위탁계약발행의 의미

베네피아 몰어드민의 다음 설정이 존재한다.

```text
벤더사 관리
  └ 계약구분: 위탁계약 업체
      └ 발행구분: 위탁계약발행
```

`위탁계약발행`은 일반적으로 다음 의미로 해석한다.

> 베네피아가 판매와 결제 처리를 대행하지만 현금영수증은 실제 매출 귀속자인 해당 벤더사의 사업자번호와 상호로 발급한다.

즉, 단순히 화면에 벤더사 이름을 표시하는 것이 아니다.

다음 정보가 벤더사 기준으로 처리되어야 한다.

- 현금영수증 공급자 사업자번호
- 현금영수증 상호
- 국세청 신고 주체
- 과세·면세 구분
- 발급 및 취소 주체
- 부분취소 시 잔액 관리

모든 위탁계약 업체가 반드시 벤더사 명의로 발행되는 것은 아니다. 몰어드민에서 `위탁계약발행`으로 선택된 업체만 벤더사 명의 발행 대상이다.

## 8. 기존 발급 구조

기존 현금영수증 시스템은 NXmile을 사용했다.

NXmile은 공개된 현금영수증 발행 시스템이며, 기존 베네피아 연동에서는 벤더별 발행을 지원하지 않거나 구현하지 않았다.

따라서 모든 거래를 베네피아 사업자번호로 일괄 발급했다.

```text
일반 판매
위탁 판매
특정 벤더 상품
복수 벤더 주문
        ↓
모두 베네피아 사업자번호로 발행
```

기존 구조가 당장 문제없이 운영된 이유는 다음과 같은 가능성이 있다.

- 위수탁 계약 및 내부 정산자료로 매출 귀속을 별도 관리
- 시스템 제약으로 인해 베네피아 명의로 통일
- 회계·세무 부서에서 별도 대사 및 보정
- 기존 계약상 수탁자 명의 발행이 허용되었을 가능성
- 세무상 최적 구조라기보다 시스템상 타협안이었을 가능성

신규 구조에서는 계약상 실제 매출 귀속자를 현금영수증 발행 주체에도 반영하려는 것으로 본다.

## 9. 토스페이먼츠의 `businessNumber`

토스페이먼츠 현금영수증 발급 API에는 공개 문서에 표시되지 않은 히든 파라미터 `businessNumber`가 존재한다.

개념적인 요청 예시:

```json
{
  "amount": 50000,
  "orderId": "ORD12345_V001",
  "orderName": "상품명",
  "type": "소득공제",
  "customerIdentityNumber": "01012345678",
  "taxFreeAmount": 5000,
  "businessNumber": "1234567890"
}
```

파라미터의 역할:

```text
customerIdentityNumber
= 현금영수증을 받는 구매자 식별정보

businessNumber
= 현금영수증을 발행하는 사업자의 사업자번호
```

발급 기준:

```text
위탁계약발행 벤더
→ businessNumber = 해당 벤더사 사업자번호

그 외 벤더
→ businessNumber = 베네피아 사업자번호
```

## 10. 복수 벤더 주문의 발급 방식

하나의 주문 안에 여러 발행 사업자가 존재하면 현금영수증 API를 발행 사업자별로 여러 번 호출해야 한다.

예시 원 주문:

```text
원 주문번호: ORD12345

A벤더 상품: 30,000원
B벤더 상품: 20,000원
```

발급 요청:

```text
ORD12345_V001
→ amount: 30,000원
→ businessNumber: A벤더 사업자번호

ORD12345_V002
→ amount: 20,000원
→ businessNumber: B벤더 사업자번호
```

### 10.1 주문번호 생성 규칙

추천 형식:

```text
{원주문번호}_{벤더고유ID}
```

예시:

```text
ORD12345_V001
ORD12345_V002
```

동일 벤더에 대해 여러 건으로 나눌 가능성이 있다면 순번을 추가한다.

```text
{원주문번호}_{벤더고유ID}_{순번}
```

예시:

```text
ORD12345_V001_01
ORD12345_V001_02
```

### 10.2 벤더사명을 직접 사용하지 않는 이유

다음과 같은 문제 때문에 벤더사명 대신 불변의 내부 식별자를 사용하는 것이 안전하다.

- 벤더사명 변경 가능
- 한글, 공백, 특수문자 문제
- 동일한 상호 존재 가능
- 주문번호 최대 길이 제한
- 재처리 및 취소 시 동일 값 재구성 어려움

## 11. 발행 단위

이 구조에서 현금영수증 발행 단위는 원 주문이 아니다.

```text
현금영수증 발행 단위
= 원 주문 + 벤더사 또는 발행 사업자
```

다만 여러 벤더가 모두 베네피아 사업자번호로 발행되는 경우, 실제 API 호출을 발행 사업자번호 기준으로 합산할지는 별도 정책 결정이 필요하다.

예시:

```text
A벤더 → 베네피아 명의 발행
B벤더 → 베네피아 명의 발행
C벤더 → C벤더 명의 발행
```

가능한 방식 1:

```text
A벤더 1건
B벤더 1건
C벤더 1건
```

가능한 방식 2:

```text
베네피아 명의 합산 1건
C벤더 명의 1건
```

부분취소와 추적 편의성을 고려하면 내부 원장은 최소한 벤더별로 유지하는 것이 안전하다.

---

## 12. 내부 원장에 저장해야 할 정보

현금영수증 원장은 원 주문번호만으로 관리하면 안 된다.

최소 권장 항목:

```text
원 주문번호
현금영수증용 주문번호
벤더사 ID
발행 사업자번호
발행 사업자 유형
발행 금액
면세 금액
과세 금액
고객 인증수단
현금영수증 유형
토스 응답 식별키
receiptKey 또는 거래 식별값
발급 상태
발급 일시
취소 누적 금액
취소 누적 면세 금액
남은 취소 가능 금액
실패 코드
실패 메시지
재처리 횟수
```

추천 키 개념:

```text
원주문번호 + 벤더ID + 발행순번
```

## 13. 취소 및 부분취소

벤더별로 발급했다면 취소도 벤더 발급 건 기준으로 처리해야 한다.

예시:

```text
원 주문 ORD12345

A벤더 현금영수증: 30,000원
B벤더 현금영수증: 20,000원
```

A벤더 상품 10,000원을 취소한 경우:

```text
ORD12345_V001 발급 건에서 10,000원 부분취소
ORD12345_V002 발급 건은 변경 없음
```

취소 시 다음을 확인해야 한다.

- 취소 대상 상품의 벤더사
- 원 발급 건의 사업자번호
- 원 발급 건의 토스 식별키
- 취소금액
- 취소금액 중 면세금액
- 기존 누적 취소금액
- 남은 취소 가능 금액

발급 시 사용한 `businessNumber`와 취소 대상 원거래의 사업자번호가 반드시 일치해야 하는지도 확인해야 한다.

## 14. 과세·면세 혼합 발급

벤더별 발급금액 안에 과세상품과 면세상품이 섞여 있다면 해당 벤더 발급 요청의 `taxFreeAmount`에 면세상품 금액을 전달한다.

예시:

```text
B벤더 전체 발급금액: 20,000원
B벤더 면세상품 금액: 5,000원
```

요청:

```json
{
  "orderId": "ORD12345_V002",
  "amount": 20000,
  "taxFreeAmount": 5000,
  "businessNumber": "B벤더 사업자번호"
}
```

의미:

```text
현금영수증 총 발급액: 20,000원
면세 금액: 5,000원
과세 대상 금액: 15,000원
```

## 15. 기존 구조와 신규 구조 비교

### 15.1 기존 NXmile 구조

```text
모든 거래
→ 베네피아 사업자번호
→ 주문당 또는 기존 시스템 기준으로 발급
```

특징:

- 벤더별 사업자번호 미사용
- 실제 매출 귀속자와 발행자가 다를 수 있음
- 내부 정산자료로 보정 필요
- 벤더별 취소 및 추적이 어려울 수 있음

### 15.2 토스페이먼츠 신규 구조

```text
위탁계약발행 벤더
→ 해당 벤더 businessNumber

그 외 벤더
→ 베네피아 businessNumber
```

특징:

- 발행 사업자 기준 다건 호출
- 주문번호에 벤더 구별자 필요
- 벤더별 발급 원장 필요
- 벤더별 취소·부분취소 처리 필요
- 실제 매출 귀속 주체와 현금영수증 발행 주체를 일치시킬 수 있음

if (vendor.isConsignmentContract()

- 부분취소 시 `taxFreeAmount` 계산 규칙
- 동일 주문의 다건 발행 허용 여부
- 중복 `orderId` 요청 시 처리 방식
- 타임아웃 후 실제 발급 여부 조회 방법

사내에서 확인해야 할 항목:

- 배송비의 발행 사업자 귀속 기준
- 최초배송비 및 추가배송비의 벤더 귀속
- 반품배송비·교환배송비의 현금영수증 처리

- 벤더별 발급 실패 시 전체 주문 성공 여부
- 일부 벤더만 발급 성공한 경우 재처리 정책

## 18. 장애 및 멱등성 고려사항

한 주문에서 여러 번 API를 호출하므로 부분 성공 상황이 발생할 수 있다.

예시:

```text
A벤더 발급 성공
B벤더 발급 실패
C벤더 발급 성공
```

이 경우 전체 주문 기준으로 단순 성공·실패만 저장하면 안 된다. 발급 건별 상태를 저장해야 한다.

권장 상태 예시:

```text
READY
REQUESTED
SUCCESS
FAILED
CANCEL_REQUESTED
PARTIALLY_CANCELED
CANCELED
```

멱등성 처리 시 다음을 고려한다.

- 동일 `orderId`로 재요청하지 않도록 관리
- 타임아웃 발생 시 무조건 신규 주문번호로 재발급하지 않음
- 먼저 토스 조회 API로 실제 발급 여부 확인
- 성공 응답 저장 실패를 대비한 재조회 로직
- 벤더별 요청 단위의 재처리
- 중복 현금영수증 발급 방지

## 19. 최종 정리

이번 변경의 핵심은 단순한 현금영수증 API 교체가 아니다.

기존에는 NXmile 연동 구조의 한계로 모든 거래를 베네피아 사업자번호로 발급했다.

신규 토스페이먼츠 연동에서는 `businessNumber`를 이용해 계약상 실제 발행 주체를 지정한다.

```text
위탁계약발행 벤더
→ 벤더사 사업자번호로 발급

그 외 벤더
→ 베네피아 사업자번호로 발급
```

하나의 주문에 여러 벤더가 포함되면 다음과 같이 처리한다.

```text
원주문번호_벤더식별자
```

형식의 고유 주문번호를 생성하여 벤더 또는 발행 사업자 단위로 현금영수증 API를 여러 번 호출한다.

따라서 시스템 설계의 핵심은 다음과 같다.

- 발행 사업자 결정
- 현금성 결제금액 산정
- 벤더별 과세·면세 금액 집계
- 고유 주문번호 생성
- 벤더별 발급 원장 관리
- 부분 성공 및 재처리
- 벤더 단위 취소·부분취소
- 중복 발급 방지
