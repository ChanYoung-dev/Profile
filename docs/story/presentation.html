개발 생산성의 역설

AI가 오히려
개발 속도를 늦춥니다

+19%

개발자들이 AI 도구를 사용할 때,
사용하지 않을 때보다 19% 더 오래 걸린다.

출처: METR.org, “Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity”, 2025

왜 늦어질까 · 이유 1

컨벤션이 일관되지 않으면
AI 결과도 일관되지 않다

  • 코드를 이해하는 데 오랜 시간이 걸린다.
  • 일관성 없는 결과물이 누적되며 리뷰·수정 비용이 커진다.
예) 우리 프로젝트는 MyBatis 형식이지만 AI가 JPA로 작성해 버린다.
왜 늦어질까 · 이유 2

컨텍스트가 없거나 너무 길면
AI는 "그럴듯한 일반론"으로 답한다

"교환완료 / 반품완료 이후에는 주문상태를 변경할 수 없다"

  • 이 정책이 문서화되어 있지 않거나, 문서가 있어도 AI가 못 찾으면
  • AI는 일반적인 주문 시스템 기준으로 판단해 버린다.
왜 늦어질까 · 이유 3

도구 활용 편차가 크다

AI를 그냥 채팅창처럼 쓰는 사람 vs. 탐색·수정·테스트·문서화를 연결해 쓰는 사람 — 생산성은 완전히 다르다.

그냥 쓰는 사람

"이 기능 추가해줘"

VS
이렇게 쓰는 사람
  1. 관련 정책 문서 먼저 찾아라
  2. 기존 컨벤션을 확인해라
  3. 수정 후보 파일을 제시해라
  4. 변경 전 영향 범위를 정리해라
  5. 최소 수정으로 구현해라
  6. 테스트 케이스를 추가해라
  7. 사이드이펙트를 리뷰해라
  8. Jira용 사업부 설명을 작성해라
왜 늦어질까 · 이유 4

코드베이스가 클수록
AI의 탐색 비용도 커진다

작은 프로젝트에서는 AI가 빠릅니다. 하지만 MSA + 레거시 + 도메인 정책 + 여러 API가 얽힌 환경은 다릅니다.

예를 들어 주문 생성 하나만 해도 —

이렇게 얽혀 있으면 AI가 전체를 다 읽기 어렵습니다.
원인 1 · AI 도구 활용 범위

AI 도구를 코딩에만 쓰기 때문

코딩은 전체 업무의 20%일 뿐 — 설계·검증·소통이 빙산의 대부분을 차지한다.

전환점

같은 도구, 하지만 다른 결과

  • AI는 비결정적 → 개인 역량이 곧 생산성
  • 조직이 아닌 사람에게 기대는 상황
  • → 조직 단위로 끌어올릴 방법이 필요하다
단단한 토대 = AI-DLC (Spec Driven Develop) + 컨텍스트 관리
해법의 등장

AI-DLC의 등장

AI 관리형 (AI-Managed)

사용자는 비즈니스 목표만 설정, 실행은 AI가 주도 — 최종 단계에서만 인간이 테스트.

✕ 단점 통제 불가 — 잘못된 방향도 끝에서야 발견, 도메인 정책·세부 요구 누락 위험
AI 보조형 (AI-Assisted)

사용자가 특정 작업(Task)에 한해 AI를 간헐적으로 활용.

✕ 단점 파편적 — 작업마다 사람이 개입, 일관성·전체 맥락이 끊기고 개인 역량에 의존
→ 그 중간에서 AI-DLC가 등장한다.

컨텍스트란? 없어도, 너무 많아도 문제

하나의 세션에서 컨텍스트 윈도우가 계속 쌓인다 — 프롬프트를 거듭할수록 점점 무거워진다.

A 프롬프트컨텍스트 ▮ → B 프롬프트컨텍스트 ▮▮ → … 프롬프트컨텍스트 ▮▮▮▮ → Z 프롬프트컨텍스트 ▮▮▮▮▮▮▮▮

구현 방법

이를 위한 구현 방법

Skills

반복되는 작업 규율·도메인 지식을 재사용 가능한 스킬로 캡슐화 — 필요할 때 자동 호출.

Subagents

독립된 컨텍스트로 작업을 병렬·격리 실행 — 메인 세션의 컨텍스트를 가볍게 유지.

Hooks

이벤트(PreToolUse·PostToolUse·Stop)에 규칙·워크플로우를 자동 강제 — 수정 후 자동 테스트·린트, 위험 동작 차단.

MCP

사내 문서·Jira·DB 등 외부 컨텍스트를 표준 프로토콜로 연결 — "그럴듯한 일반론" 대신 실제 근거로 답하게.
