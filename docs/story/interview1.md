# **멀티프로세스/멀티쓰레드**

**WHY?**

저는 거래량과 가격추세를 기반으로 하는 전략을 구사했다. 기본적으로 거래량이 터지고 가격이 최고가나 최저가일때 그리고 특정 수학적수치를 만족할때 매수/매도를 하는 그런 전략이었다.

이때 몇분봉 기반으로할지, 또 손익비는 몇으로 할지, 또 기간은 몇개의 봉으로 할지, 손절라인은 기준베이스에 몇배로 잡을지, 거래량이 몇퍼센트 터졌을때할지 등등 많은 입력값에 따라 결과값들이 다양하게 바뀌었다. 이런식으로 입력값이 대략 10가지정도였다.

이런 입력값들을 다양하게 주어 수억까지의 케이스들을 백테스트하여 최적의 해를 구해야했는데 단일쓰레드로만으로는 백테스트에 한계를 느껴 멀티프로세스나 멀티쓰레드를 도입하기로하였다

# **(문제점)멀티쓰레드/멀티프로세스 차이 왜 멀티프로세스를 도입하였는지?**

처음에는 멀티쓰레드는 동시성이고 멀티프로세스가 병렬성이라고 생각되어 멀티프로세스를 채택하였다.

또한 **OOM으로부터 멀티프로세스가 더 자유롭기때문입니다. 메모리를 따로 사용하기때문에 장애가 격리되어있고 해당 워커프로세스**만 죽기때문입니다.

그리고 마지막으로 공유메모리의 난이도 입니다. 저는 갯수는 별로 없지만 데이터양이 큰 공유데이터가 존재하였다. 자바스크립트에서는 SharedArrayBuffer를 이용하여 힙에 공유데이터을 사용하는데, race condition 때문에 쓰기작업이 까다롭고 세마포어와 같은 기법을 적용하기엔 데드락의 위험성도 크기때문에 안전한 멀티프로세스를 선택하였습니다. 보통 멀티쓰레드는 스택을제외한 힙/데이터 영역을 공유하지만 자바스크립트는 다릅니다. 자바스크립트는 SharedArrayBuffer라고 명시적으로 선언해야 공유데이터로 사용 가능합니다. 이 SharedArrayBuffer는 공유메모리이기ㅏ때문에 race condition때문에 쓰기작업이 까다롭고 쓰기라고 해서 변수 = ‘1231’ 이개념이 아니라 slice와 map 같은 논리적 쓰기때문에

**왜냐하면: “쓰기”의 정의를 잘못 잡고 있기 때문**

보통 말하는 “쓰기”는 이거다 👇

```jsx
ohlcv[i] = 123;   // 명시적 write
```

하지만 **SharedArrayBuffer에서 위험한 쓰기**는 이것도 포함한다 👇

❌ **위험한 “논리적 쓰기”**

```jsx
slice()
map()
filter()
concat()
spread(...)
Math.max(...arr)
```

+ 하나의 변수를 다같이 공용으로 쓰니까 메모리 누적이 되어 **OOM이나 배열 더블리사이징오류**와 같은 위험에 노출될 가능성이 크다

그리고 또한 멀티프로세스에서도 IPC를 이용하거나 mmap를 사용하여 커널을 통해 직접 가상메모리에 데이터를 매핑하는 방법도 있으므로..

그러나 mmap는 윈도우에서 지원하지않기때문에 병렬컴퓨팅에 적합하지않았다.

**해결방안**

결국 멀티프로세스에서 워커프로세스에게 공유 데이터들을 할당할때 IPC통해 broadcast를 하는데.. 데이터가 너무 커서 IPC통해 전달이 안된다. 이를 해결하기위해 json파일을 사용한다.

: 마스터프로세스에서 파일형식으로 대용량 데이터를 분산저장하고 워커프로세스에서 저장된 파일을 읽어서 메모리 할당.

**메모리 문제점과 해결방안**

OOM이나 Array사이즈 문제가 있었습니다. 아무래도 병렬환경에서 변수를 잘 못 써서 생긴문제로 생각되었습니다. 이를 해결하기 위해 **“한 번에 처리하지 않고, 나눠서 처리하고, 즉시 비운다”는 원칙**으로 구조를 변경했습니다.

힙데이터 용량을 주기적으로 체크하는 로직을 작성하고 특정 용량이 넘은 경우  힙스냅샷을 찍어서 분석한다.

힙스냅샷을 분석한뒤 OOM을 유발할수있는 변수들을 확인합니다. 대용량 배열과 같은 데이터는 나눠서 해결합니다. 입력같은경우 수백만 케이스를 직접 워커프로세스에게 할당하지않고 BATCH만큼 나눠서 할당합니다. 결과값들을 INSERT할때도 마찬가지입니다. 워커프로세스에게 받은 결과값들을 즉시 I/O작업하거나 한꺼번에 모아서  I/O작업하지않고 CHUNK 사이즈로 나눠서 해결한다. 전역변수에 결과들을 담으면 메모리가 점점 누적되서 OOM이 발생되므로, CHUNK사이즈를 설정하고 해당 갯수마다  I/O작업를 실행하며 I/O작업이끝나면 flush하여 데이터를 날리고 json으로 결과를 저장하여 메모리를 비워둔다.

(마지막으로.. 확실하게 메모리를 비우기위해 LARGE_BATCH만큼 채워지면 프로세스들을  완전재시작하여 초기화작업을 진행한다.)

또한 전역변수를 지양하고, 사용한 뒤에는 사용안하는 것을 null값을 명시적으로 입력하여 가비지컬렉션이 수거하도록한다.

GC에 기대기보다, 메모리가 오래 살아남지 않도록 구조 자체를 바꿔서 OOM을 해결했습니다.

**How 백테스트?**

전체기간동안 백테스트를 하지않고 일부기간까지만 백테스트합니다. 예를 들면 저같은 걍우 2023년 5월부터 2024년 8월로 백테스트를진행합니다. 그리고 특정 수익이상이 발생한 결과들을 전부 모아서 다시 다시한번더 현재까지 데이터를 백테스트합니다 이때 2024년 8월부터 현재까지 수익이 올랐는지 안올랐는지를 확인합니다. 해당 데이터 통계들을 ai에게 입력하여 어떤 성향의 입력값들이 높은 성과를 대체적으로 나타내는지 어떤 값들의 조합이 가장 최적의 해인지 추출하여 선정된 녀석들을 자동매매로 돌립니다.

또한 시각적 데이터 분석과 한번더 백테스트 검증목적으로 트레이딩뷰에도 트레이딩뷰코드를 이용하여 최종적으로 백테스트를 진행합니다.

**자동매매**

자동매매는 가용성이 중요합니다 단 몇초라도 시스템이 죽으면 안되기때문에 소켓을 기본적으로 사용하되 가용성을 확보해놓는 구조로 API 구조도 마련했습니다. 예를들면 ccxt라는 라이브러리를 사용하는데 해당 라이브러리에 문제가 생겼을 경우에 대비하여 적정 retry 이후에는 바이낸스거래소에 직접 쏘도록 구현햇습니다. 이마져도 안되는 경우 로컬 변수에 담아놓은 데이터를 참고하여 처리되도록 하였습니다.

또한 해외거래소와 타임싱크를 맞추기 위해 주기적으로 시스템 타임싱크를 업데이트하고, 실시간으로 오류를 확인하기위해 오류 발생시 텔레그램으로 저에게 알려주도록 구현해놨습니다.

# MQ

# **왜 MQ를 도입했는가?**

초기에는 주문과 관련된 모든 처리를 동기식으로 구현했는데, 실제 운영을 하다 보니 몇 가지 한계를 명확히 느끼게 됐습니다.

첫 번째는 **외부 시스템 지연 문제가 있**습니다. 동기식으로 외부api를 호출하는데 외부api응답이 오래걸릴경유 사용자입장에선 기다려야한다는 문제가 있습니다. 또한 주문 API가 그 시간 동안 블로킹되면서 그 사이 들어오는 요청들이 계속 쌓이면서 서블릿 스레드 풀이 고갈되어 전체 서비스가 응답하지 못하는 문제가 발생할 수 있었습니다.

두 번째는 **후행 작업의 장애 전파 문제**였습니다. 주문을 예시로 들면 결제완료를 하고 현금영수증API를 호출하여 현금영수증처리를 합니다. 이게 하나의 주문 프로세스로 묶여있는데요 이때 현금영수증 발급  실패하면 장애가 전파되어 주문 완료 자체가 실패하거나 롤백되는 구조였고, 실제 비즈니스 중요도에 비해 과도한 결합이 발생하고 있었습니다. 또한 try catch로 잡는다해도 out of memory같은 장애에 취약합니다. 왜냐하면 같은 서버에 존재하기때문입니다.

세번째로는 대용량 트래픽에 대응하기 위함입니다. 일반 사용자들은 모바일앱이나 PC웹사이트에서 한건씩 주문을 취소하지만, 벤더사 같은 경우는 api호출 또는 엑셀파일을 통해서 다량의 주문을 동시에 호출할 수 있습니다. 이러한 요청들이 여러개가 동시에 들어올때 주문API가 뻗을 수 있는 위험이 있다.

마지막으로, **대량 상품 INSERT 같은 배치성 작업**에서는 단일 트랜잭션으로 처리하다 보니 타임아웃, 롤백 비용, DB 부하가 커지는 문제가 반복적으로 발생했습니다. 이때 MQ를 도입하면 Queue가 버퍼역할을 하여 대규모트래픽에도 장애가 없는 시스템을 구축할수있습니다.

rabbitmq를통해 긴 지연시간은 비동기호출로 해결하고 장애전파, out of memory와 같은 장애도 분리된환경이기때문에 방지할수있습니다. **대규모트래픽케이스에도 병목지점을 파악하여 mq를 도입해 트래픽에도 안정성있게 설계할수있습니다.**

**어려웠던것1: 재기동시 유실 ⇒ TCC패턴과 unique인덱스  적용**

동시성제어, 같은 ordId에 대해서는 큐내에서 순차적으로 동기식으로 처리되어야함.

## 시도한 방법들

### 1. 샤딩 (직접 구현)

`hash(ordNo) % 4 → 큐 4개 분산
같은 ordNo → 항상 같은 큐 → 같은 서버

채택 안 한 이유:
  인프라 종속적 (hostname 고정 필요)
  → affinity + spread로 보완 가능하지만
  → 논의 끝에 다른 방법 검토`

### 2. PROC_LOCK_ID (DB 락)

`취소 대상 row에 messageId를 UPDATE로 선점
다른 서버가 같은 row 접근 시 차단

채택 안 한 이유:
  락 해제 누락 시 영구 잠금
  재기동 복구 로직 복잡
  스케줄러 의존
  비즈니스 테이블 오염`

### 3. Outbox Pattern

`MQ Consumer는 TASK 저장만
Scheduler가 순서대로 처리

채택 안 한 이유:
  RabbitMQ 의미 없어짐
  그냥 처음부터 DB에 저장하면 됨`

### 4. x-single-active-consumer ← 시도했으나 실패

`큐에 여러 Consumer 연결되어 있어도
1개만 active → 순서 보장

채택 안 한 이유:
  RabbitMQ 3.8.0 이상 필요
  현재 버전 3.7.8 → 동작 안 함`

### 5. Exclusive Consumer ← 최종 채택 ✅

`Consumer 연결 시 exclusive=true
1개 서버만 연결 허용
나머지 3개 서버는 3초마다 재시도 대기
active 서버 장애/재기동 시 자동 승격`

---

## 최종 채택 — Exclusive Consumer

`장점:
  RabbitMQ 버전 무관 (3.7.x 동작)
  큐 변경 없이 Consumer 설정만 변경
  active 서버 장애 시 자동 승격
  코드 단순

단점:
  장애 복구 공백 최대 9초
  (heartbeat=10, recoveryInterval=3초)
  대기 서버 3개가 3초마다 재시도 로그 발생`

`그래도 이슈사항 : 컨테이너를 재기동 했는데 재기동중에도 새로운 요청을 받아서 요청인 진행되다가 중간에 유실되는 문제 - Spring lifecyle이 바뀌지않고 노마드에 의해 강제종료됨 
고려해야할점: nomard time-out, consul healthCheck, spring lifecyle(graceful), mq-heartbeat, recoveryInterval 
위 고려사항을 통해 도커파일에서 java 명령어가 아닌 exec를 붙인 java 명령어를 실행하여 OS레벨에서의 SIGTERM 전달할수있음`

주문의 핵심 흐름과 후행 작업을 분리하고, 처리 시간이 길거나 실패 가능성이 있는 작업은 MQ 기반 비동기 처리로 전환했습니다. 그 결과 주문 API의 응답 속도와 안정성이 개선되고, 외부 장애가 주문 전체로 전파되는 문제를 효과적으로 차단할 수 있었습니다.

# **테스트코드도입**

## **WHY 왜 테스트코드 도입을 했는가?**

주문 도메인은 배송, 결제, 쿠폰, 포인트, 상품 등 여러 도메인이 복잡하게 정책으로 얽혀 있었고, 결제, 취소, 반품 등 다양한 시나리오를 포함하고 있습니다. 이로 인해 특정 기능을 일부 수정하거나 정책을 추가하더라도 사이드 이펙트가 발생할 위험이 있고 광범위한 수동 검증이 필요해 개발 효율성을 크게 낮추었습니다. 이를 위해 핵심 usecase에 대해 시나리오 테스트코드 작성을 진행하였습니다.

## **난관**

**MSA에서의 통합테스트**

통합테스트를 하는데는 여러 어려움이 있었습니다.

 하나의 어려움은 통합 테스트 수행 시 데이터계층를 어떻게 다룰 것인가에 대한 고민이었습니다.  Mock 기반 테스트, Alpha DB, 테스트 전용 DB, In-Memory DB, TestContainer 등 다양한 대안에 대해서 고민하게되었습니다.
 처음에는 테스트환경에서도 개발DB에 붙여서 통합테스트를 진행하였습니다. 쉽게 구성할 수 있는 장점이 있었지만 테스트환경 오염이라는 문제가 생깁니다.  
 예를들면 주문한번하면 주문갯수는 한개늘어야한다. 이를 테스트하기위해 DML을 구현하였지만 테스트동시에 누군가 외부에서 주문을 한 경우 주문갯수는 1늘어야한다는게 통과되지않습니다. 즉, 범위, 정산, 통계와 같은 테스트에 적합하지않습니다. 또한 분산트랜잭션 롤백 문제가 생깁니다. 주문API를 주문 테스트를 하는데 포인트API를 통해 포인트를 발급처리하면 테스트가 끝났을때 포인트를 롤백시켜줘야하는 문제가 있습니다. 

2번째로 msa내 타 프로젝트와 통신할때 모킹처리에 대한 문제가 있습니다.예를들어 주문api와 포인트api가 있을 경우 주문할때 포인트차감때문에 주문api에서 포인트api를 호출합니다. 이때 포인트api에서 주문api에서 사용하는 db에 쓰기작업이 있으면 주문api테스트에 포인트api에 의존적인 문제가 생깁니다.이는 msa구조에서 db를 공유해서 생긴문제로써 이렇게 설계를 하면 안되는 이유를 깨달았고, msa에서의 경계처리를 잘해야한다는 것을 깨달았습니다.

이러한 테스트환경 오염문제때문에 개발DB를 사용하지않고 TestContainer를 통해 환경을 구축하였습니다. 이로 인해 외부 환경에 영향을 받지 않는 **격리된 테스트 환경을 구축할 수 있었고, 포인트API DB커밋내역을 따로 롤백할 필요없이 TestÇontainer를 다시 띄우면 해결할수있었습니다.  또한 포인트API에서의 주문관련로직은 주문API로 옮김으로써 경계선을 확실히 하여 포인트API를 모킹할수있었고 이로인해 테스트하고자하는 영역을 명확하게 테스트할수있었습니다.  테스트의 재현성과 신뢰성을 크게 높일 수 있었습니다.**

2번째로 준비데이터를 만드는데 있었습니다. 예를들어 주문취소를 테스트하려면 주문이라는 선행위에 대한 데이터가 있어야하고 그리고 주문관련된 상품데이터 세팅등이 필요합니다. 이를 위해 개발DB에 세팅되어있는 데이터들의 DML을 주입하여 테스트환경을 구축하였습니다. 직접 로컬에 테스트컨테이너를 보도록 상품API띄우고 상품API를 통해 상품생성한뒤 주문을 실행하는 배경 로직을 태우고 그 뒤 주문취소 통합테스트를 하는 방식으로 진행헤야하는데 너무많은 시간이 할애되어 배보다 배꼽이 더 커지는 격이라 트레이드오프로 전자를 차선책으로 선택하였습니다.

세번째로  타api 통신 방식처리 문제입니다. 외부api인걍우 단순하게 모킹처리를 하면 되지만 msa내에서의 다른 api와  통신은 고려해야할 점이 있습니다. 그냥 모킹처리를 하거나 아니면 실제로 연동하는 방식 두가지 방법이 있을텐데 정석적으로는 외부api처럼 mocking 처리하는 것이 맞지만 DB를 공유하는 msa에서는 타API에서 주문관련DB를 조작할수가 있으므로 타API의 호출된 부분 로직들을 하나하나 다봐야하는 까다로운 어려움이 있었습니다. 이를 통해 MSA 구축에있어서 환경구축이 주용하단걸 알았습니다.

분산트랜잭션 롤백처리입니다

 처음에는 단순히 개발DB를 미리 세팅하여 테스트하였습니다. 예를 들어 초도배송비 복구를 테스트해야하는경우, 주문완료된 주문건과 해당 주문에 필요한 상품 정보 등등이 필요합니다. 해당 행위들을 직접 실행하고 쌓인 개발DB데이터를 가지고  DELETE 및 INSERT 을 통해 DML스냅샷을 뽑아놓은다음 TC전에 해당 DML을 실행하여 마치 주문한 것처럼 만들고 TC테스트를 하였습니다. 
 비교적 쉽게 통합테스트를 작성할수 있었지만 여러 문제가 생겼습니다. 우선, **할수있는 테스트가 한정적**입니다. 예를들면 주문한번하면 주문갯수는 한개늘어야한다. 이를 테스트하기위해 DML을 구현하였지만 테스트동시에 누군가 외부에서 주문을 한 경우 주문갯수는 1늘어야한다는게 통과되지않습니다. 즉, 범위, 정산, 통계와 같은 테스트에 적합하지않습니다. 또한 **SQL로 선행된 행위를 판단**해야하기때문에 이해하기 어렵다는 문제가 존재한다.

**결론**

모든 테스트에 테스트컨테이너를 사용하지않고 핵심 코어는 TestContainer사용하고 비동기작업이 없고 외부API호출이없는 방식에는 @Sql을 쓰는 방식으로 해결

2번째 난관은 MSA 환경에서의 테스트는 또 다른 난관이었습니다. 예를 들어 주문테스트를 진행한다고 하면, 주문 API에 대한 통합 테스트를 수행하기 위해서는 상품 정보가 필수였는데, 이 상품 데이터가 어느 경로를 통해 제공되어야 하는지부터가 문제였습니다. ①개발기 상품 API를 호출할 것인지, ②로컬에 상품 API를 띄워 연동할 것인지, 혹은 ③ 개발 DB에 이미 존재하는 상품DB를 사용하는 것이 맞는지에 대한 판단이 필요했습니다. 더불어 서비스 간 트랜잭션이 분리된 MSA 구조 특성상, 분산 트랜잭션 흐름을 테스트 환경에서 어떻게 검증하고 제어할 것인지 역시 쉽지 않은 문제였습니다.

# XSS

세 번째로 어려웠던 경험은 ISMS 대응 과정에서 XSS 관련 이슈를 해결했던 경험입니다.

당시 서비스는 MSA 구조인데, 보안 정책이 서비스별로 일관되지 않게 적용되어 있었습니다.

어떤 서비스는 XSS 필터나 인터셉터가 적용되어 있었고, DB에 이스케이프 처리를 하고 또 어떤 프로젝트는 화면단에서 이스케이프 처리를 하는등 다양한 방식으로 대응하였습니다.

일부 서비스는 필터 단계와 컨트롤러 단에서 각각 이스케이프 처리가 이루어져 **이중 처리 문제가 발생하거나 MSA 즉 분산시스템구조때문에 여러 API을 거치면서 여러번치환되는 경우가 존재하였습니나.**

저또한 XSS 정책을 정비하여 배포를 진행했지만, 일부 데이터가 JSON을 문자열로 저장하고 있는 구조에서 작은따옴표가 이스케이프 처리되며 **JSON 파싱 오류가 발생해 롤백을 경험하기도 했습니다.**

이 경험을 통해 단순히 보안 이슈를 개별적으로 대응하는 것이 아니라,

**MSA 환경에서는 보안 정책 역시 통일된 기준과 공통 적용 방식이 필요하다는 점**을 명확히 인식하게 되었습니다.

이후에는 **정보보안 부서와 협업하여 통일된 XSS 처리 기준을 수립하고, 케이스별 해결책을 정리한 뒤**,

이를 모든 서비스에 공통으로 적용하기 위해 **애노테이션 기반의 공통 처리 방식으로 구현하고 전사에 가이드 하였습니다. 이가이드를 조직원들이 잘따라와준결과**

그 결과 다음 해 ISMS 점검에서**XSS 관련 지적 건수를 기존 대비 크게 감소시키는 성과를 낼 수 있었고 MSA에서의 XSS 처리방식에 대해 배울수있었습니다.**

힘든점

MSA와 XSS 특성상 단일 서비스가 아닌 **여러 서비스를 함께 검증해야 하는 구조적인 어려움**이 있었지만 ..

정책

1. DB에 저장이 되는가? DB에 저장이 되지않는다면 단순히 escape처리하여 노출합니다. 예를 들면 검색어같이 DB에 저장되지않고 그대로 화면단에 뿌리는 경우 컨트롤러에서 escape처리하여 노출하면됩니다. 이때 jsonString형식인 경우 string말고 json데이터를 객체형식으로 받아오도록 합니다. 왜냐면 따옴표도 escape 처리되어 json파싱에 오류가 생길수도있끼때문입니다.
2. DB에 저장하는 경우 escape처리해서 DB한테 넣어놓고, 다른 곳에서 수정하는 부분이 없는지 확인합니다. 예를 들면 PC에서 마이페이지내 리뷰를 escape처리해서 넣어놨는데 모바일 마이페이지 리뷰 보기부분에서는 cout처리가 되어 이스케이프문자 그대로 노출되는 문제들이 있을수있고 해당 리뷰를 수정하면 이중 이스케이프 처리될수있으며, 상품상세쪽에 있는 리뷰에서도 텍스트처리되어 이스케이프문자그대로 노출되는 문제현황도 확인해야합니다. 결국 모든 영향도를 확인해야합니다

# 객체지향

다섯 번째로 어려웠던 경험은 주문 결제 도메인을 객체지향적으로 리팩토링했던 경험입니다.

저는 주문 결제 도메인 담당자로서, 카드 결제, 포인트 결제, 간편 결제 등 여러 결제 수단과

복합 결제까지 함께 처리해야 하는 구조를 담당하고 있었습니다.

초기 구현은 결제 방식에 따라 분기하는 형태였고,

결제 수단이 늘어나고 정책이 추가될수록 **if-else 조건문이 계속 증가하는 구조**였습니다.

이 방식은 처음에는 직관적이었지만,

정책 변경이나 신규 결제 수단 추가 시마다 기존 로직을 수정해야 했고

그로 인해 사이드 이펙트가 발생하기 쉬운 구조였습니다.

이 과정에서 단순히 if 문을 줄이는 것이 목적이 아니라,

- *변경되는 이유를 조건문이 아닌 객체의 책임으로 옮겨야 한다*는 문제의식을 갖게 되었습니다.

즉, 결제 방식을 **객체로 표현하는 전략 패턴을 도입하였습니다.**

→전략패턴이란? 

“행위를 객체로 캡슐화해서, 런타임에 자유롭게 선택하고 교체할 수 있게 만드는 패턴”

**결제에는 여러가지 방식이 있는데 이를 추상화하여 인터페이스를 만들고 이를 구현하는 구현체를 여러개가 만든다.그리고 실행 즉 런타임중에 동적으로 전략에 따라 구현체를 선택 및 교체하는 패턴입니다.**

같은 인터페이스를 구현한 여러 빈이 존재할 경우,

Spring은 이를 Map 형태로 해당 빈들을 자동 주입해줄 수 있다.

그 결과 결제 방식에 따른 행위 분기는 if 문이 아니라

**다형성을 통해 자연스럽게 해결되는 구조**로 변경할 수 있었습니다.

또한 결제 방식 선택 로직은 팩토리로 캡슐화하여,

클라이언트 코드에서는 결제 수단의 구체적인 타입을 알 필요 없이

추상화에만 의존하도록 설계했습니다.

이로써 새로운 결제 수단이 추가되더라도

기존 결제 로직을 수정하지 않고 확장할 수 있는 구조를 만들 수 있었습니다.

이 리팩토링을 통해 저는 if 문 자체가 문제가 아니라,**변경 가능성이 높은 정책을 조건문으로 처리하는 것이 문제**라는 점을 체감했고,
SOLID 원칙, 특히 OCP와 DIP는 이러한 문제를 해결하기 위한 방법이 될수도있겠다라는 교훈을 얻었습니다.

# **MSA 및 주문고도화**

기술적인 장점

- 복잡한 MSA 환경에서도 주문·결제·배송처럼 정합성이 생명인 도메인을 안정적으로 운영하는 것이 장점입니다.
- 분산트랜잭션, rabbitmq 등을 이용하여 장애 전파를 최소화하며 실제 운영 중 결함 없이 안정적으로 서비스를 유지해온 경험이 있습니다.
- 객체지향적 코드 작성과 핵심 시나리오 중심의 테스트코드 도입을 통해 정책 변경이나 기능 확장에도 흔들리지 않는 구조를 개발하고 그결과 장애 평균 복구 시간를 줄일수 있었습니다.

## **교환신청레퍼토리**

주문테이블에는 교환수량 칼럼이 있습니다. 해당 칼럼에는 0이상만 존재할수있는데 -1이 존재하는 문제가 있었습니다. 이 문제는 여러가지 경로로 유입될수있습니다. 일명 따닥으로 인해 생긴문제이거나 사용자가 화면 두개를 키거나 이런식으로 사용자 휴먼에러로 인해 유입될수있고 시스템 에러로 인해 유입될수있습니다. 이러한 오류를 해결하기 위해 교환신청시 교환완료/교환거부만 있는지 검증하였는데  교환신청인지도 확인하도록 검증추가하였습니다. 물론 프론트단에서도 방어로직을 구현했습니다.

 하지만 동시성문제가 존재할수있습니다. 오라클은 ReadCommited 관점이기때문에 매쿼리마다 최신 커밋을 반영하기때문에 Dirty Read와 같은 문제가 적습니다. 그러나 여전히 Read Committed도 경쟁 조건 자체를 해결해주지는 않기 때문에 멱등성을 위한 중복감지로직과 낙관적 락 확보가 필요합니다.

## **연마감문제**

주문취소시 기존에는 카드취소 -> 포인트취소 형식 이었다. 그러나 카드는 취소되었지만 연마감으로인해 포인트취소가 불가한 형식이 존재한다. 이럴때 MSA이기때문에 카드결제에 대해 INSERT 한 값들을 SAGA패턴 방식으로 돌려야한다. DB에 올린작업들은 SAGA패턴방식으로 보상트랜잭션해결하면 되지만 카드취소요청을 취소하기 위해 외부API에게 요청을 다시 날려야하지만 취소원복은 불가하므로.. 카드만 취소되는 문제가 발생한다. 이를 위해 포인트취소를 가장 먼저 실행하는 것으로 바꾸었다. 물론 이때도 문제가 존재한다. 포인트취소를 하였지만 카드취소가 불가한 경우인데 이경우에 단순히 포인트 취소를 원복해주면 되지않나싶지만 외부포인트를 혼용해서 쓰는 포인트인경우 취소원복이 불가하다. 하지만 카드취소가 불가한경우는 점검과같은 경우밖에 없으므로 거의 드물다. 이때는 어쩔수없이 KCP에게 싹싹 비는수밖에없다.

## 결제수단과 실결제수단차이

프론트단에서 신용카드를 선택했지만 주문API에서는 카카오가 선택되는 현상

KCP에서 신용카드를 선택하고 신용카드 앱에서 카카오를 선택할수 있는 문제가 생겨서 kcp에서는 카카오결제수단을 반환하는 문제가 생긴다. 이를 방지하기위해 사용자의 request와 kcp의 리턴값을 비교하여 데이터를 검증하는 로직을 추가하여 해결

## **MSA에서의 한방쿼리**

일반적으로 MSA에서는 DB도 분리해야한다.

DB가 분리되지않으면 회원테이블 칼럼이 수정되었을때 해당 테이블을 사용하는 서비스들을 전부 다 재기동해야한다.

DB까지 분리하면 한방쿼리가 힘들다.. 그렇다면?

**방법1. API조합방법(API Aggregation)**

각각의 API들을 호출하여 조합하는 방식

**방법2. CQRS + READ전용모델**

주문완료이벤트가 발행되면 주문이력테이블(READ전용테이블)에 INSERT하는 이벤트를 발행하도록 처리

둘의 차이 => API조합은 각각 서비스가 살아있어야하지만 CQRS는 각각의 서비스가 죽어도 주문이력은 확인가능하다는 장점

기존에는 상품결제테이블과 배송비결제테이블을 따로 분리해서 운영하였다. 상품결제테이블에 주문번호, 상품순번 이 존재하고 배송비결제테이블에 주문번호,상품순번이 존재하며 주문번호상품순번으로 서로ㅜ강결합되어있는 구조였다. 그렇기때문에 상품이 정산되면 배송비는 정산을 못하는구조가되었고 이로인해 배송비만 취소가 불가능한 케이스도 생겼다. 

또한 n:1구조이기때문에 반품배송비를 데이터에 넣을수가 없었다. 판매자귀책사유만 생각했기때문이다. 이로인해 반춤배송비는 계좌이체로 하는 번거로움이 생겼고,

이를해결하기위해 배송비을 상품취급하여 상품결제테이블에 같이 넣었고 반품배송비와 같은 여러배송비구조를 채택하기위해 관계테이블을 도입하야 n:n방식으로 해결하였다

상품과개별적으로 정산처리가능하였고 귀책에따라 반품배송비추가도가능하도록 하였다.

그뿐만아니라 판매자귀책일때 조건부가 안될시 추가배송비를 받지않는 구조도 가능하게되었다.

초도배송비
초도배송비개념: 상품을 주문할 경우 상품가격과 더불어 배송비가 발생되는데 이때 결제되는 배송비가 초도배송비
초도배송비는 취소시에는 배송비까지 처리되나 반품시에는 배송비가 반환되지않는다.
이때 귀책사유가 판매자귀책사유라면 배송비를 반환해줘야하는데 이를 초도배송비 복구라한다. 또한 반품배송비를 왕복배송비(초도배송비+반품배송비)로 입금한 경우, 구매자귀책이어도 초도배송비가 중복결제됐기때문에 초도배송비 복구처리해줘야한다.

cf) 취/반품시 생긴 추가배송비는 초도배송비로 신용카드 결제요청을 하고 재결제처리를 하였으나, 반품배송비는 계좌이체로 벤더가 고객에게 요청함

그러므로 DB데이터상 조건으로는

- 관련된 묶음상품이 취소되어야한다. 이때 모든 상품이라하면 같은 벤더사로 묶인 상품을 말한다. 묶은상품들은 하나의 배송을 갖기때문에 묶은상품들이 모두 취소되어야지 배송이 무효화되기때문에 배송비를 취소할수있는것이다.

예외사항, 고려할점

- 배송비결제데이터는 상품결제데이터와 주문번호,상품순번으로 매핑되어있다.상담사측에서 잘못 요청할수도있기때문에 해당상품순번에 관련된 묶음상품들이 모두 취소되었는지 확인하는 과정이 필요하다.
- 베네피아에서는 월정산을 기준으로 정산마감을 내린다. 월정산이 넘어갔는지도 확인해야한다. 요청받은 상품순번이 월정산이 끝난경우 복구가 불가하다. 왜냐하면 상품과 배송비는 상품순번으로 매핑되어있는 강결합구조이기때문에 상품이 월정산이 끝난경우 복구가 불가하다.

로직처리핵심

- 배송비와 상품은 1:N 구조이다. 예를들어 상품순번 1,2,3 이 묶음상품이라면 하나의 배송비가 묶여있다. 이때 배송비는 하나의 상품순번에만 매핑을 시킨다. 이때 묶음상품 중 특정상품이 취소될때마다 배송비가 다른 결제가 살아있는 상품순번에 묶이는 구조로 되어있다. 이러한 구조때문에 모든상품이 취소되더라도 취소순서에 따라 배송비가 붙어있는 상품순번이 다르다. 이러한 구조를 상담사는 모르기때문에 실제 취소하려는 배송비와 ㄱ연결된 상품순번을 찾는 로직을 구현한다.
이러한 구조때문에 반품배송비가 표현하기 어렵다. 그렇기 때문에 반품배송비는 계좌이체하는 형식으로 처리했다..
- 이렇게 상품순번과 배송비는 강결합 구조이기때문에 해당 상품순번에 사용된 배송비 결제수단이 상품결제에 사용안된 결제수단에 없는 경우 해당 결제수단도 상품결제테이블에 넣어줘야한다.
