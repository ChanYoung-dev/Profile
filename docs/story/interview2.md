# **1.멀티프로세스/멀티쓰레드**

**WHY?**

저는 거래량과 가격추세를 기반으로 하는 전략을 구사했다. 기본적으로 거래량이 터지고 가격이 최고가나 최저가일때 그리고 특정 수학적수치를 만족할때 매수/매도를 하는 그런 전략이었다.

이때 몇분봉 기반으로할지, 또 손익비는 몇으로 할지, 또 기간은 몇개의 봉으로 할지, 손절라인은 기준베이스에 몇배로 잡을지, 거래량이 몇퍼센트 터졌을때할지 등등 많은 입력값에 따라 결과값들이 다양하게 바뀌었다. 이런식으로 입력값이 대략 10가지정도였다.

이런 입력값들을 다양하게 주어 수억까지의 케이스들을 백테스트하여 최적의 해를 구해야했는데 단일쓰레드로만으로는 백테스트에 한계를 느껴 멀티프로세스나 멀티쓰레드를 도입하기로하였다

# **(문제점)멀티쓰레드/멀티프로세스 차이 왜 멀티프로세스를 도입하였는지?**

처음에는 멀티쓰레드는 동시성이고 멀티프로세스가 병렬성이라고 생각되어 멀티프로세스를 채택하였다.

또한 **OOM으로부터 멀티프로세스가 더 자유롭기때문입니다. 메모리를 따로 사용하기때문에 장애가 격리되어있고 해당 워커프로세스**만 죽기때문입니다.

그리고 마지막으로 공유메모리의 난이도 입니다. 저는 갯수는 별로 없지만 데이터양이 큰 공유데이터가 존재하였다. 자바스크립트에서는 SharedArrayBuffer를 이용하여 힙에 공유데이터을 사용하는데, race condition 때문에 쓰기작업이 까다롭고 세마포어와 같은 기법을 적용하기엔 데드락의 위험성도 크기때문에 안전한 멀티프로세스를 선택하였습니다. 보통 멀티쓰레드는 스택을제외한 힙/데이터 영역을 공유하지만 자바스크립트는 다릅니다. 자바스크립트는 SharedArrayBuffer라고 명시적으로 선언해야 공유데이터로 사용 가능합니다. 이 SharedArrayBuffer는 공유메모리이기ㅏ때문에 race condition때문에 쓰기작업이 까다롭고 쓰기라고 해서 변수 = ‘1231’ 이개념이 아니라 slice와 map 같은 논리적 쓰기때문에

**왜냐하면: “쓰기”의 정의를 잘못 잡고 있기 때문**

보통 말하는 “쓰기”는 이거다 👇

```jsx
ohlcv[i] = 123;   // 명시적 write
```

하지만 **SharedArrayBuffer에서 위험한 쓰기**는 이것도 포함한다 👇

❌ **위험한 “논리적 쓰기”**

```jsx
slice()
map()
filter()
concat()
spread(...)
Math.max(...arr)
```

+ 하나의 변수를 다같이 공용으로 쓰니까 메모리 누적이 되어 **OOM이나 배열 더블리사이징오류**와 같은 위험에 노출될 가능성이 크다

그리고 또한 멀티프로세스에서도 IPC를 이용하거나 mmap를 사용하여 커널을 통해 직접 가상메모리에 데이터를 매핑하는 방법도 있으므로..

그러나 mmap는 윈도우에서 지원하지않기때문에 병렬컴퓨팅에 적합하지않았다.

**해결방안**

결국 멀티프로세스에서 워커프로세스에게 공유 데이터들을 할당할때 IPC통해 broadcast를 하는데.. 데이터가 너무 커서 IPC통해 전달이 안된다. 이를 해결하기위해 json파일을 사용한다.

: 마스터프로세스에서 파일형식으로 대용량 데이터를 분산저장하고 워커프로세스에서 저장된 파일을 읽어서 메모리 할당.

**메모리 문제점과 해결방안**

OOM이나 Array사이즈 문제가 있었습니다. 아무래도 병렬환경에서 변수를 잘 못 써서 생긴문제로 생각되었습니다. 이를 해결하기 위해 **“한 번에 처리하지 않고, 나눠서 처리하고, 즉시 비운다”는 원칙**으로 구조를 변경했습니다.

힙데이터 용량을 주기적으로 체크하는 로직을 작성하고 특정 용량이 넘은 경우  힙스냅샷을 찍어서 분석한다.

힙스냅샷을 분석한뒤 OOM을 유발할수있는 변수들을 확인합니다. 대용량 배열과 같은 데이터는 나눠서 해결합니다. 입력같은경우 수백만 케이스를 직접 워커프로세스에게 할당하지않고 BATCH만큼 나눠서 할당합니다. 결과값들을 INSERT할때도 마찬가지입니다. 워커프로세스에게 받은 결과값들을 즉시 I/O작업하거나 한꺼번에 모아서  I/O작업하지않고 CHUNK 사이즈로 나눠서 해결한다. 전역변수에 결과들을 담으면 메모리가 점점 누적되서 OOM이 발생되므로, CHUNK사이즈를 설정하고 해당 갯수마다  I/O작업를 실행하며 I/O작업이끝나면 flush하여 데이터를 날리고 json으로 결과를 저장하여 메모리를 비워둔다.

(마지막으로.. 확실하게 메모리를 비우기위해 LARGE_BATCH만큼 채워지면 프로세스들을  완전재시작하여 초기화작업을 진행한다.)

또한 전역변수를 지양하고, 사용한 뒤에는 사용안하는 것을 null값을 명시적으로 입력하여 가비지컬렉션이 수거하도록한다.

GC에 기대기보다, 메모리가 오래 살아남지 않도록 구조 자체를 바꿔서 OOM을 해결했습니다.

**How 백테스트?**

전체기간동안 백테스트를 하지않고 일부기간까지만 백테스트합니다. 예를 들면 저같은 걍우 2023년 5월부터 2024년 8월로 백테스트를진행합니다. 그리고 특정 수익이상이 발생한 결과들을 전부 모아서 다시 다시한번더 현재까지 데이터를 백테스트합니다 이때 2024년 8월부터 현재까지 수익이 올랐는지 안올랐는지를 확인합니다. 해당 데이터 통계들을 ai에게 입력하여 어떤 성향의 입력값들이 높은 성과를 대체적으로 나타내는지 어떤 값들의 조합이 가장 최적의 해인지 추출하여 선정된 녀석들을 자동매매로 돌립니다.

또한 시각적 데이터 분석과 한번더 백테스트 검증목적으로 트레이딩뷰에도 트레이딩뷰코드를 이용하여 최종적으로 백테스트를 진행합니다.

자동매매는 가용성이 중요합니다 단 몇초라도 시스템이 죽으면 안되기때문에 소켓을 기본적으로 사용하되 가용성을 확보해놓는 구조로 API 구조도 마련했습니다. 예를들면 ccxt라는 라이브러리를 사용하는데 해당 라이브러리에 문제가 생겼을 경우에 대비하여 적정 retry 이후에는 바이낸스거래소에 직접 쏘도록 구현햇습니다. 이마져도 안되는 경우 로컬 변수에 담아놓은 데이터를 참고하여 처리되도록 하였습니다.

# 2.MQ

## why?

초기에는 주문과 관련된 모든 처리를 동기식으로 구현했는데, 실제 운영을 하다 보니 몇 가지 한계를 명확히 느끼게 됐습니다.

첫 번째는 **외부 시스템 지연 문제가 있**습니다. 동기식으로 외부api를 호출하는데 외부api응답이 오래걸릴경유 사용자입장에선 기다려야한다는 문제가 있습니다. 또한 주문 API가 그 시간 동안 블로킹되면서 그 사이 들어오는 요청들이 계속 쌓이면서 서블릿 스레드 풀이 고갈되어 전체 서비스가 응답하지 못하는 문제가 발생할 수 있었습니다.

두 번째는 **후행 작업의 장애 전파 문제**였습니다. 주문을 예시로 들면 결제완료를 하고 현금영수증API를 호출하여 현금영수증처리를 합니다. 이게 하나의 주문 프로세스로 묶여있는데요 이때 현금영수증 발급  실패하면 장애가 전파되어 주문 완료 자체가 실패하거나 롤백되는 구조였고, 실제 비즈니스 중요도에 비해 과도한 결합이 발생하고 있었습니다. 또한 try catch로 잡는다해도 out of memory같은 장애에 취약합니다. 왜냐하면 같은 서버에 존재하기때문입니다.

세번째로는 대용량 트래픽에 대응하기 위함입니다. 일반 사용자들은 모바일앱이나 PC웹사이트에서 한건씩 주문을 취소하지만, 벤더사 같은 경우는 api호출 또는 엑셀파일을 통해서 다량의 주문을 동시에 호출할 수 있습니다. 이러한 요청들이 여러개가 동시에 들어올때 주문API가 뻗을 수 있는 위험이 있다.

마지막으로, **대량 상품 INSERT 같은 배치성 작업**에서는 단일 트랜잭션으로 처리하다 보니 타임아웃, 롤백 비용, DB 부하가 커지는 문제가 반복적으로 발생했습니다. 이때 MQ를 도입하면 Queue가 버퍼역할을 하여 대규모트래픽에도 장애가 없는 시스템을 구축할수있습니다.

rabbitmq를통해 긴 지연시간은 비동기호출로 해결하고 장애전파, out of memory와 같은 장애도 분리된환경이기때문에 방지할수있습니다. **대규모트래픽케이스에도 병목지점을 파악하여 mq를 도입해 트래픽에도 안정성있게 설계할수있습니다.**

주문부분취소시 국세청에서 부분취소는 없기때문에 이전현금영수증처리금액 전액취소api요청하고 그다음 남은 결제금액을 다시 국세청에게 api호출한다. 그러나 이 때,  Consumer1에게 취소요청이 도달하고 Consumer2에게 결제요청API가 도달한다. 그러나 Consumer1은 busy한 상태이고 Consumer2는 널널한 상태일때 결제api호출이 먼저 실행되고 취소api호출이 나중에 실행된다.결국 이때 국세청에게 결제Api호출한 건은 이미기처리된건이라는 오류가 나타난다.

# **테스트코드도입**

## **WHY 왜 테스트코드 도입을 했는가?**

주문 도메인은 배송, 결제, 쿠폰, 포인트, 상품 등 여러 도메인이 복잡하게 정책으로 얽혀 있었고, 결제, 취소, 반품 등 다양한 시나리오를 포함하고 있습니다. 이로 인해 특정 기능을 일부 수정하거나 정책을 추가하더라도 사이드 이펙트가 발생할 위험이 있고 광범위한 수동 검증이 필요해 개발 효율성을 크게 낮추었습니다. 이를 위해 핵심 usecase에 대해 시나리오 테스트코드 작성을 진행하였습니다.

## **난관**

### 1.persistence layer(개발DB사용문제)

 하나의 어려움은 통합 테스트 수행 시 데이터계층를 어떻게 다룰 것인가에 대한 고민이었습니다.  Mock 기반 테스트, Alpha DB, 테스트 전용 DB, In-Memory DB, TestContainer 등 다양한 대안에 대해서 고민하게되었습니다.
 처음에는 테스트환경에서도 개발DB에 붙여서 통합테스트를 진행하였습니다. 쉽게 구성할 수 있는 장점이 있었지만 테스트환경 오염이라는 문제가 생깁니다.  
 예를들면 주문한번하면 주문갯수는 한개늘어야한다. 이를 테스트하기위해 DML을 구현하였지만 테스트동시에 누군가 외부에서 주문을 한 경우 주문갯수는 1늘어야한다는게 통과되지않습니다. 즉, 범위, 정산, 통계와 같은 테스트에 적합하지않습니다.

### 2.분산트랜잭션 롤백 문제

 msa환경이기때문에 생기는 문제. 주문API를 주문 테스트를 하는데 포인트API를 통해 포인트를 발급처리하면 테스트가 끝났을때 포인트를 롤백시켜줘야하는 문제가 있습니다. 

→ 이러한 테스트환경 오염문제때문에 개발DB를 사용하지않고 TestContainer를 통해 환경을 구축하였습니다. 이로 인해 외부 환경에 영향을 받지 않는 **격리된 테스트 환경을 구축하고 테스트컨테이너덕분에 포인트API DB커밋내역을 따로 롤백할 필요없이 TestÇontainer를 다시 띄우면 해결할수있었습니다**

### 3. MSA내 타API 처리

2번째로 msa내 타 프로젝트와 통신할때 모킹처리에 대한 문제가 있습니다.예를들어 주문api와 포인트api가 있을 경우 주문할때 포인트차감때문에 주문api에서 포인트api를 호출합니다. 이때 포인트api에서 주문api에서 사용하는 db에 쓰기작업이 있으면 주문api테스트에 포인트api에 의존적인 문제가 생깁니다.이는 msa구조에서 db를 공유해서 생긴문제로써 이렇게 설계를 하면 안되는 이유를 깨달았고, msa에서의 경계처리를 잘해야한다는 것을 깨달았습니다.

**→ 포인트API에서의 주문관련로직은 주문API로 옮김으로써 경계선을 확실히 하여 포인트API를 모킹할수있었고 이로인해 테스트하고자하는 영역을 명확하게 테스트할수있었습니다 또한 확실한 경계선이 보장되므로 mocking을 처리하여 실제 api통신 필요없이 테스트의 안정성을 확보할수 있습니다.  테스트의 재현성과 신뢰성을 크게 높일 수 있었습니다.**

### 4. 테스트 데이터 세팅

준비데이터를 만드는데 있었습니다. 예를들어 주문취소를 테스트하려면 주문이라는 선행위에 대한 데이터가 있어야하고 그리고 주문관련된 상품데이터 세팅등이 필요합니다. 이를 위해 첫번째로 개발DB에 이미 존재하는 상품데이터를 DML로 따서 그대로 @sql을 통해 데이터를 세팅하는방법이 존재한다. 
두번째로는 직접 로컬에서 상품API가 테스트컨테이너를 보도록 상품API를 띄우고 상품API를 통해 상품생성한뒤 주문API에서 주문을 실행하는 배경 로직을 태우고 그 뒤 주문취소 통합테스트를 하는 방식으로 진행헤야합니다.
아벙삭아 실제 환경과 유사하면 유사할수록 테스트코드의 신뢰성이 높아지지만 테스트코드에 더많은 구축 및 개발비용에 시간이 소요됩니다. 너무많은 시간이 할애되어 배보다 배꼽이 더 커지는 격이라 트레이드오프로 전자를 차선책으로 선택하였습니다
하지만 핵심 시나리오는 후자를 선택했습니다. 이 때 msa에서의 테스트컨테이너를 실행하기위해 테스트마다 테스트컨테이너를 실행하는 것은 너무 오랜시간이걸린다. 테스트컨테이너를 자바 프로젝트로 하나 따서 테스트컨테이너생성전용 프로젝트를 만들어 테스트컨테이너를 띄운다음 상품API와 주문API 필요한 프로젝트에 test환경파일에 테스트컨테이너환경을 연동함으로써 해당 테스트컨테이너를 보도록 한다.

당시 서비스는 MSA 구조인데, 보안 정책이 서비스별로 일관되지 않게 적용되어 있었습니다.

어떤 서비스는 XSS 필터나 인터셉터가 적용되어 있었고, DB에 이스케이프 처리를 하고 또 어떤 프로젝트는 화면단에서 이스케이프 처리를 하는등 다양한 방식으로 대응하였습니다.

일부 서비스는 필터 단계와 컨트롤러 단에서 각각 이스케이프 처리가 이루어져 **이중 처리 문제가 발생하거나 MSA 즉 분산시스템구조때문에 여러 API을 거치면서 여러번치환되는 경우가 존재하였습니나.**

저또한 XSS 정책을 정비하여 배포를 진행했지만, 일부 데이터가 JSON을 문자열로 저장하고 있는 구조에서 작은따옴표가 이스케이프 처리되며 **JSON 파싱 오류가 발생해 롤백을 경험하기도 했습니다.**

이 경험을 통해 단순히 보안 이슈를 개별적으로 대응하는 것이 아니라,

**MSA 환경에서는 보안 정책 역시 통일된 기준과 공통 적용 방식이 필요하다는 점**을 명확히 인식하게 되었습니다.

이후에는 **정보보안 부서와 협업하여 통일된 XSS 처리 기준을 수립하고, 케이스별 해결책을 정리한 뒤**,

이를 모든 서비스에 공통으로 적용하기 위해 **애노테이션 기반의 공통 처리 방식으로 구현하고 전사에 가이드 하였습니다. 이가이드를 조직원들이 잘따라와준결과**

그 결과 다음 해 ISMS 점검에서**XSS 관련 지적 건수를 기존 대비 크게 감소시키는 성과를 낼 수 있었고 MSA에서의 XSS 처리방식에 대해 배울수있었습니다.**

힘든점

MSA와 XSS 특성상 단일 서비스가 아닌 **여러 서비스를 함께 검증해야 하는 구조적인 어려움**이 있었지만 ..

정책

1. DB에 저장이 되는가? DB에 저장이 되지않는다면 단순히 escape처리하여 노출합니다. 예를 들면 검색어같이 DB에 저장되지않고 그대로 화면단에 뿌리는 경우 컨트롤러에서 escape처리하여 노출하면됩니다. 이때 jsonString형식인 경우 string말고 json데이터를 객체형식으로 받아오도록 합니다. 왜냐면 따옴표도 escape 처리되어 json파싱에 오류가 생길수도있끼때문입니다.
2. DB에 저장하는 경우 escape처리해서 DB한테 넣어놓고, 다른 곳에서 수정하는 부분이 없는지 확인합니다. 예를 들면 PC에서 마이페이지내 리뷰를 escape처리해서 넣어놨는데 모바일 마이페이지 리뷰 보기부분에서는 cout처리가 되어 이스케이프문자 그대로 노출되는 문제들이 있을수있고 해당 리뷰를 수정하면 이중 이스케이프 처리될수있으며, 상품상세쪽에 있는 리뷰에서도 텍스트처리되어 이스케이프문자그대로 노출되는 문제현황도 확인해야합니다. 결국 모든 영향도를 확인해야합니다

# 객체지향

다섯 번째로 어려웠던 경험은 주문 결제 도메인을 객체지향적으로 리팩토링했던 경험입니다.

저는 주문 결제 도메인 담당자로서, 카드 결제, 포인트 결제, 간편 결제 등 여러 결제 수단과

복합 결제까지 함께 처리해야 하는 구조를 담당하고 있었습니다.

초기 구현은 결제 방식에 따라 분기하는 형태였고,

결제 수단이 늘어나고 정책이 추가될수록 **if-else 조건문이 계속 증가하는 구조**였습니다.

이 방식은 처음에는 직관적이었지만,

정책 변경이나 신규 결제 수단 추가 시마다 기존 로직을 수정해야 했고

그로 인해 사이드 이펙트가 발생하기 쉬운 구조였습니다.

이 과정에서 단순히 if 문을 줄이는 것이 목적이 아니라,

- *변경되는 이유를 조건문이 아닌 객체의 책임으로 옮겨야 한다*는 문제의식을 갖게 되었습니다.

즉, 결제 방식을 **객체로 표현하는 전략 패턴을 도입하였습니다.**

→전략패턴이란? 

“행위를 객체로 캡슐화해서, 런타임에 자유롭게 선택하고 교체할 수 있게 만드는 패턴”

**결제에는 여러가지 방식이 있는데 이를 추상화하여 인터페이스를 만들고 이를 구현하는 구현체를 여러개가 만든다.그리고 실행 즉 런타임중에 동적으로 전략에 따라 구현체를 선택 및 교체하는 패턴입니다.**

같은 인터페이스를 구현한 여러 빈이 존재할 경우,

Spring은 이를 Map 형태로 해당 빈들을 자동 주입해줄 수 있다.

그 결과 결제 방식에 따른 행위 분기는 if 문이 아니라

**다형성을 통해 자연스럽게 해결되는 구조**로 변경할 수 있었습니다.

또한 결제 방식 선택 로직은 팩토리로 캡슐화하여,

클라이언트 코드에서는 결제 수단의 구체적인 타입을 알 필요 없이

추상화에만 의존하도록 설계했습니다.

이로써 새로운 결제 수단이 추가되더라도

기존 결제 로직을 수정하지 않고 확장할 수 있는 구조를 만들 수 있었습니다.

이 리팩토링을 통해 저는 if 문 자체가 문제가 아니라,**변경 가능성이 높은 정책을 조건문으로 처리하는 것이 문제**라는 점을 체감했고,
SOLID 원칙, 특히 OCP와 DIP는 이러한 문제를 해결하기 위한 방법이 될수도있겠다라는 교훈을 얻었습니다.

## 이후 STORY

### **교환신청레퍼토리**

주문테이블에는 교환수량 칼럼이 있습니다. 해당 칼럼에는 0이상만 존재할수있는데 -1이 존재하는 문제가 있었습니다. 이 문제는 여러가지 경로로 유입될수있습니다. 일명 따닥으로 인해 생긴문제이거나 사용자가 화면 두개를 키거나 이런식으로 사용자 휴먼에러로 인해 유입될수있고 시스템 에러로 인해 유입될수있습니다. 이러한 오류를 해결하기 위해 교환신청시 교환완료/교환거부만 있는지 검증하였는데  교환신청인지도 확인하도록 검증추가하였습니다. 물론 프론트단에서도 방어로직을 구현했습니다.

 하지만 동시성문제가 존재할수있습니다. 오라클은 ReadCommited 관점이기때문에 매쿼리마다 최신 커밋을 반영하기때문에 Dirty Read와 같은 문제가 적습니다. 그러나 여전히 Read Committed도 경쟁 조건 자체를 해결해주지는 않기 때문에 멱등성을 위한 중복감지로직과 낙관적 락 확보가 필요합니다.

### **연마감문제**

주문취소시 기존에는 카드취소 -> 포인트취소 형식 이었다. 그러나 카드는 취소되었지만 연마감으로인해 포인트취소가 불가한 형식이 존재한다. 이럴때 MSA이기때문에 카드결제에 대해 INSERT 한 값들을 SAGA패턴 방식으로 돌려야한다. DB에 올린작업들은 SAGA패턴방식으로 보상트랜잭션해결하면 되지만 카드취소요청을 취소하기 위해 외부API에게 요청을 다시 날려야하지만 취소원복은 불가하므로.. 카드만 취소되는 문제가 발생한다. 이를 위해 포인트취소를 가장 먼저 실행하는 것으로 바꾸었다. 물론 이때도 문제가 존재한다. 포인트취소를 하였지만 카드취소가 불가한 경우인데 이경우에 단순히 포인트 취소를 원복해주면 되지않나싶지만 외부포인트를 혼용해서 쓰는 포인트인경우 취소원복이 불가하다. 하지만 카드취소가 불가한경우는 점검과같은 경우밖에 없으므로 거의 드물다. 이때는 어쩔수없이 KCP에게 싹싹 비는수밖에없다.

### 결제수단과 실결제수단차이

프론트단에서 신용카드를 선택했지만 주문API에서는 카카오가 선택되는 현상

KCP에서 신용카드를 선택하고 신용카드 앱에서 카카오를 선택할수 있는 문제가 생겨서 kcp에서는 카카오결제수단을 반환하는 문제가 생긴다. 이를 방지하기위해 사용자의 request와 kcp의 리턴값을 비교하여 데이터를 검증하는 로직을 추가하여 해결

### 살아있는 수량

배송준비중지연, 클레임중지연 건이 얼마인지 확인할때 살아있는 주문건에 대해서만 통계를 내야한다. 취소되거나 교환된 상품은 노출되면 안되기때문이다. 이 때 노출되어야하는 기준을 배송준비중지연인데 반품신청은 노출되어야하는가? 와 같은 문제가 존재한다. 비슷하게 직권취소가능한 주문을 볼때 반품진행중인 건에 대해서는 직권취소가 가능한 것인가? 와 같은 정책문제가 존재한다.

주문한건에 대해 리뷰작성촉구알람을 보낸다했을때 이때 교환중인 주문건은 해당사항일지,반품신청건은 해당사항일지 

직권취소의 경우에는 반품거부,교환거

# **아쉬운점**

- 데이터계층에서 모든 것이 다 녹아들어가있는 즉 한방쿼리에 대한 아쉬움, 이로인해 절차지향적 코드 만능 dto로 인해 객체지향적 사고할 기회가 없어서 아쉽다..

- DB까지 분리된 MSA 단계에서 어떻게 한방쿼리를 대체하는지 제가 아는 방식이 맞는지 경험해보고싶습니다

**MSA에서의 한방쿼리**

- 일반적으로 MSA에서는 DB도 분리해야한다.

- DB가 분리되지않으면 회원테이블 칼럼이 수정되었을때 해당 테이블을 사용하는 서비스들을 전부 다 재기동해야한다.

- DB까지 분리하면 한방쿼리가 힘들다.. 그렇다면?

**방법1. API조합방법(API Aggregation)**

각각의 API들을 호출하여 조합하는 방식

**방법2. CQRS + READ전용모델**

주문완료이벤트가 발행되면 주문이력테이블(READ전용테이블)에 INSERT하는 이벤트를 발행하도록 처리

둘의 차이 => API조합은 각각 서비스가 살아있어야하지만 CQRS는 각각의 서비스가 죽어도 주문이력은 확인가능하다는 장점


# 주문고도화

기존에는 상품결제테이블과 배송비결제테이블을 따로 분리해서 운영하였다. 상품결제테이블에 주문번호, 상품순번 이 존재하고 배송비결제테이블에 주문번호,상품순번이 존재하며 주문번호상품순번으로 서로 강결합되어있는 구조였다. 그렇기때문에 상품이 정산되면 배송비는 정산을 못하는구조가되었고 이로인해 배송비만 취소가 불가능한 케이스도 생겼다. 

또한 n:1구조이기때문에 반품배송비를 데이터에 넣을수가 없었다. 판매자귀책사유만 생각했기때문이다. 이로인해 반춤배송비는 계좌이체로 하는 번거로움이 생겼고,

이를해결하기위해 배송비을 상품취급하여 상품결제테이블에 같이 넣었고 반품배송비와 같은 여러배송비구조를 채택하기위해 관계테이블을 도입하야 n:n방식으로 해결하였다

상품과개별적으로 정산처리가능하였고 귀책에따라 반품배송비추가도가능하도록 하였다.

그뿐만아니라 판매자귀책일때 조건부가 안될시 추가배송비를 받지않는 구조도 가능하게되었다.

즉,
몰고도화 프로젝트에서 주문·배송비 구조를 개선한 경험이 있습니다.
기존 시스템은 상품결제 테이블과 배송비결제 테이블이 분리되어 있었고 주문번호와 상품순번으로 강하게 연결된 구조였습니다.

이 구조에서는 배송비가 특정 상품에 종속되기 때문에 여러 운영 문제가 발생했습니다.
대표적으로 하나의 배송비가 여러 상품에 묶여 있는 N:1 구조였는데 배송비는 특정 상품순번 하나에만 매핑되어 있었습니다.

그래서 상품이 부분 취소될 때마다 배송비가 다른 상품으로 계속 이동하는 구조였고, 실제 취소해야 할 배송비가 어떤 상품에 연결되어 있는지 파악하기 어려운 문제가 있었습니다.
또한 이 구조에서는 반품배송비나 교환배송비 같은 추가 배송비를 데이터 구조로 표현하기 어려웠습니다.

그래서 실제 운영에서는 반품 배송비를 시스템이 아닌 계좌이체로 처리하는 수기 방식을 사용하고 있었습니다.
특히 커머스에서는 초도배송비 복구라는 케이스가 있는데 예를 들어 판매자귀책일때 배송비 환불이나 고객이 반품하면서 왕복배송비를 입금한 경우 초도배송비가 중복 결제되기 때문에 이를 다시 환불해줘야 합니다. 하지만 기존 시스템에서는 이 로직을 자동화할 수 없어서 상담사가 직접 데이터를 확인하고 수기로 처리하고 있었습니다.
이 문제의 근본 원인은 배송비가 상품에 종속된 강결합 구조라고 판단했습니다.

그래서 배송비를 독립적인 결제 대상으로 보고 배송비를 하나의 상품처럼 취급하도록 설계를 변경했습니다. 그리고 상품과 배송비 사이에 배송비 관계 테이블을 도입하여 N:N 구조로 재설계했습니다.
이 구조를 통해
* 하나의 배송비가 여러 상품에 연결될 수 있고
* 하나의 상품이 여러 배송비와 연결될 수도 있게 되었습니다.

그 결과
* 배송비만 취소하는 기능
* 반품/교환 배송비 처리
* 귀책 변경에 따른 배송비 환불
* 초도배송비 복구 자동화 

같은 다양한 커머스 정책을 시스템적으로 처리할 수 있게 되었고, 기존에 상담사가 수기로 처리하던 CS 업무도 자동화하여 운영 효율을 크게 개선할 수 있었습니다.

# 초도배송비
초도배송비개념: 상품을 주문할 경우 상품가격과 더불어 배송비가 발생되는데 이때 결제되는 배송비가 초도배송비
초도배송비는 취소시에는 배송비까지 처리되나 반품시에는 배송비가 반환되지않는다.
이때 귀책사유가 판매자귀책사유라면 배송비를 반환해줘야하는데 이를 초도배송비 복구라한다. 또한 반품배송비를 왕복배송비(초도배송비+반품배송비)로 입금한 경우, 구매자귀책이어도 초도배송비가 중복결제됐기때문에 초도배송비 복구처리해줘야한다.

cf) 취/반품시 생긴 추가배송비는 초도배송비로 신용카드 결제요청을 하고 재결제처리를 하였으나, 반품배송비는 계좌이체로 벤더가 고객에게 요청함

## 그러므로 DB데이터상 조건으로는

- 관련된 묶음상품이 취소되어야한다. 이때 모든 상품이라하면 같은 벤더사로 묶인 상품을 말한다. 묶은상품들은 하나의 배송을 갖기때문에 묶은상품들이 모두 취소되어야지 배송이 무효화되기때문에 배송비를 취소할수있는것이다.

## 예외사항, 고려할점

- 배송비결제데이터는 상품결제데이터와 주문번호,상품순번으로 매핑되어있다.상담사측에서 잘못 요청할수도있기때문에 해당상품순번에 관련된 묶음상품들이 모두 취소되었는지 확인하는 과정이 필요하다.
- 베네피아에서는 월정산을 기준으로 정산마감을 내린다. 월정산이 넘어갔는지도 확인해야한다. 요청받은 상품순번이 월정산이 끝난경우 복구가 불가하다. 왜냐하면 상품과 배송비는 상품순번으로 매핑되어있는 강결합구조이기때문에 상품이 월정산이 끝난경우 복구가 불가하다.

## 로직처리핵심

- 배송비와 상품은 1:N 구조이다. 예를들어 상품순번 1,2,3 이 묶음상품이라면 하나의 배송비가 묶여있다. 이때 배송비는 하나의 상품순번에만 매핑을 시킨다. 
- 이때 묶음상품 중 특정상품이 취소될때마다 배송비가 다른 결제가 살아있는 상품순번에 묶이는 구조로 되어있다. 이러한 구조때문에 모든상품이 취소되더라도 취소순서에 따라 배송비가 붙어있는 상품순번이 다르다. 이러한 구조를 상담사는 모르기때문에 실제 취소하려는 배송비와 연결된 상품순번을 찾는 로직을 구현한다.
  (이러한 구조때문에 반품배송비가 표현하기 어렵다. 그렇기 때문에 반품배송비는 계좌이체하는 형식으로 처리되고있었다)
- 이렇게 상품순번과 배송비는 강결합 구조이기때문에 해당 상품순번 연결된 배송비 결제수단이 상품결제에 사용된 결제수단에 없는 경우 해당 결제수단도 상품결제테이블에 넣어줘야한다.
- 즉, 배송비와 상품순번이 강결합이기때문에 상품결제에 없는 결제수단이 배송비결제수단에 존재하는 경우 상품결제에 로우를 하나추가해야한다.

# AI Tech TF (AI-DLC + Harness Engineering + AI Architecture)

## WHY — 왜 시작했는가?

AI Tech TF에서 「AI 도입 리드」로 합류하면서, 두 가지 극단을 모두 피해야 한다는 문제의식이 있었습니다.

1. **AI-Assisted의 한계**
   - GitHub Copilot, ChatGPT, Claude Code처럼 「개발자가 일부 코드를 요청하면 AI가 응답」하는 구조는, AI가 우리 회사의 정책·운영환경·MSA 구조·영향도를 모릅니다.
   - 예: 「교환완료 이후 상태변경 불가」 정책을 AI가 모르기 때문에 `order.changeStatus(CANCEL_COMPLETE)` 같은 코드를 자연스럽게 추천할 수 있고, 코드 리뷰 단계에서 잡지 못하면 운영에서 터집니다.
   - 즉, **겉보기엔 맞지만 실제 운영에서는 위험한 코드**가 생성될 가능성이 큽니다.

2. **AI-Managed(Vibe Coding)의 위험**
   - 반대로 「AI가 알아서 다 만들게 하자」고 두면, 설계·정책·보안 검증이 빠지고 기술부채만 쌓입니다.

3. **Context Fragmentation**
   - 정책 문서, 코드, 운영 로그, MSA 메타데이터가 서로 분리되어 있어서 사람이 매번 직접 문맥을 연결(Context Stitching)해야 했습니다.
   - 정책 변경 한 줄에 대해 「정책 문서 찾기 → 주문 API 찾기 → 영향도 분석 → 반품/교환 흐름 확인 → 정산 영향도 분석 → 테스트 시나리오 검토」를 사람이 매번 수행하는 비용이 너무 컸습니다.

그래서 AWS가 제안한 **AI-Driven Development Life Cycle (AI-DLC)** 의 핵심 철학:

> "AI가 실행을 주도하되(Human-in-the-loop), 인간이 통제한다."

— 이것을 우리 커머스 환경에 맞게 단계적으로 도입하기로 했습니다.

## 도입 전략을 2축으로 나눈 이유

처음에는 「Claude Code 잘 쓰자」 정도로 출발했지만, 그 수준에서는 다음 문제가 해결되지 않았습니다.

- AI가 사내 운영 데이터를 모르니 분석 깊이가 얕다 → **AI Architecture 필요**
- AI 생성 코드와 MSA 호출 체인 분석이 사람·시점마다 들쭉날쭉하다 → **Harness Engineering 필요 (docs·Skill 기반 가이드)**

그래서 2축으로 분리했습니다.

```text
[축 1] AI Architecture                  — 운영DB를 안전하게 AI에 노출하는 구조
[축 2] Harness Engineering (docs·Skill) — AI의 코드 생성·분석을 일관된 docs·Skill 가이드로 유도
```

## 축 1. AI Architecture — 커머스 운영 분석용 AI 구조 설계

### 1.1 문제 상황

커머스 운영 CS의 대표 예시:

> 「특정 고객이 주문서에 진입했을 때 사용 가능 포인트가 0원으로 표시된다」

이 한 줄 CS를 분석하려면 다음 정보가 모두 필요합니다.

- 모바일 Front / PC Front의 포인트 표시 로직
- Order API / Point API의 주문서 포인트 계산 로직
- 회원 ID, 상품 ID, 주문번호, 결제수단 기준 운영DB 데이터
- 포인트 락, 결제 대기 주문, 상품 카테고리 정책, 고객사 정책, 결제수단 정책
- 필요 시 MQ, 이벤트 이력, 로그, 캐시

**핵심 문제:** LLM이 원인 분석을 잘하려면 운영 데이터가 필요한데, 운영DB는 VDI/사내망에서만 접근 가능합니다.

### 1.2 핵심 원칙

> **LLM에 운영DB 권한을 직접 주지 않는다.**

```text
❌ 위험한 구조
LLM → 운영DB 직접 접속
(개인정보 유출, 대량 조회, Full Scan, 잘못된 SQL 실행, 감사 불가)

✅ 권장 구조
LLM → MCP/Tool Gateway → 사내망 전용 운영 API → ReadOnly DB
```

운영DB 접근 권한은 **사내망 내부의 Tool/API만** 갖고, LLM은 그 Tool을 통해서만 제한적으로 데이터를 조회합니다.

원칙:
- **Read Only**: SELECT만 가능, INSERT/UPDATE/DELETE/MERGE/DDL 금지
- **Tool Gateway**: 허용된 Tool/API만 호출 가능한 통제 계층
- **Audit**: 누가 어떤 고객/주문 데이터를 언제 조회했는지 기록
- **Masking**: 전화번호·이메일·주소·카드번호 등은 LLM에 전달하지 않거나 마스킹

### 1.3 Context API vs Diagnosis API

처음에는 「테이블별 API를 열어주면 되지 않나?」 생각했지만 그건 비추천입니다.

```text
❌ 비추천 (테이블별 API)
GET /point-info
GET /customer-product-category
GET /point-product-category
```

이렇게 만들면 AI가 조인 조건과 정책을 스스로 추론해야 하므로 위험합니다. 또한 운영 테이블 구조가 과도하게 노출됩니다.

```text
✅ 추천 (업무 Context 단위 API)
GET /context/checkout?memberId=...&productId=...&orderNo=...&paymentMethod=...
```

이 API 하나가 주문서 진입 시점의 포인트 판단에 필요한 모든 데이터를 묶어서 반환합니다.

```json
{
  "memberPoint": { "totalPoint": 50000, "availablePoint": 0, "lockedPoint": 50000 },
  "productPolicy": { "pointUsable": false, "reason": "CATEGORY_NOT_ALLOWED" },
  "paymentPolicy": { "pointAllowed": true },
  "pendingOrders": [{ "status": "PAYMENT_PENDING", "lockedPoint": 50000 }],
  "reasonHints": [
    "POINT_LOCKED_BY_PENDING_ORDER",
    "PRODUCT_CATEGORY_NOT_POINT_ELIGIBLE"
  ]
}
```

핵심은 LLM 친화적으로 **Context Normalization**을 하는 것입니다.

```json
// AS-IS (LLM이 의미를 모름)
{ "POINT_STTS_CD": "P003" }

// TO-BE (의미 자체를 코드로 표현)
{ "reason": "POINT_LOCKED_BY_PENDING_ORDER" }
```

그리고 **반복되는 CS만** Diagnosis API로 승격합니다.

```text
초기 단계 (Context API)
/context/checkout
/context/member-point
/context/order-timeline
/context/event-timeline

반복 CS 후 승격 (Diagnosis API)
/diagnosis/point/checkout-availability
/diagnosis/coupon/apply-failure
/diagnosis/cash-receipt/issue-failure
```

처음부터 다 만들지 않고 PoC → 확장 순서로 가는 게 핵심입니다.

### 1.4 외부 LLM vs 로컬 LLM

| 구분 | 외부 LLM (Claude/OpenAI/Gemini) | 로컬 LLM (Qwen/Llama/Mistral) |
| --- | --- | --- |
| 장점 | 추론력 우수, 도입 빠름 | 운영 데이터가 외부로 나가지 않음 |
| 단점 | 마스킹/요약 필수 | GPU 서버, 모델 운영 필요 |
| 운영DB 접근 | 원본 금지, Context API + reasonCode 위주 | 내부망에서 Safe SQL 또는 Context API |
| 채택 환경 | 커머스, SaaS | 금융, 방산, 망분리 환경 |

우리는 **외부 LLM 기반 사내 GPT 구조**를 1차 목표로 잡았습니다. 로컬 LLM은 보안 요구가 높아진 단계에서 검토합니다.

### 1.5 Safe SQL Tool은 후행 단계로

처음부터 LLM이 자유 SQL을 짜고 실행하게 하는 건 위험합니다. 순서:

```text
Query Template Tool → Context API → 제한된 Safe SQL Tool
```

Safe SQL Tool을 만들더라도:
- SELECT만 허용
- 허용 테이블만 조회
- 개인정보 컬럼 차단 (PHONE_NO, EMAIL, ADDRESS, CARD_NO, PASSWORD)
- SELECT * 금지, WHERE 필수, ROWNUM/FETCH FIRST 강제
- timeout / Audit / ReadOnly Replica 강제

### 1.6 도입 로드맵

```text
1단계: 운영DB 직접 접근 금지 원칙 확정
2단계: ReadOnly 계정 + 사내망 전용 API 서버 준비
3단계: 포인트/주문/결제 관련 Context API 1~2개만 PoC
4단계: MCP로 LLM이 Context API를 호출하게 연결
5단계: Audit, Masking, Auth, row limit, timeout 적용
6단계: 반복 CS를 Diagnosis API로 승격
7단계: 내부망 GPU 서버 기반 로컬 LLM 검토
8단계: 마지막으로 제한된 Safe SQL Tool 검토
```

핵심은 **「AI가 운영DB를 자유롭게 조회하게 만들기」가 아니라 「AI가 안전하게 설계된 운영 Tool을 호출하게 만들기」** 입니다.

## 축 2. Harness Engineering — docs·Skill로 AI의 코드 생성·분석을 유도

### 2.1 핵심 철학

> Claude의 「기억」에 의존하지 않고, 문서·Skill 구조로 일관된 행동을 유도한다.

```text
Claude Guide → docs (SSOT) → Skill (Task-specific)
```

Claude의 코딩 능력이 좋다고 컨벤션을 매번 「기억」할 것이라 기대하면 안 됩니다. 대신 **CLAUDE.md(라우터) + docs(GuardRail·Policy·Instruction) + Skill(작업별 플레이북)** 3단 구조로 매 작업마다 필요한 문서가 자동으로 로드되도록 설계했습니다.

### 2.2 CLAUDE.md는 라우터로 얇게 유지

처음에는 CLAUDE.md 하나에 모든 규칙을 다 넣는 실수를 했습니다. 문제:
- 컨텍스트 토큰 낭비
- 규칙 유지보수 어려움
- 작업과 무관한 규칙까지 모두 로드

해결: CLAUDE.md는 **라우터** 역할만, 세부 규칙은 docs/conventions로 분리.

```text
repo/
├── CLAUDE.md                              ← 얇은 라우터
├── docs/
│   ├── conventions/                       ← 코딩 컨벤션

│   │   ├── spring.md

│   │   ├── testing.md
│   │   └── architecture.md
```

CLAUDE.md 예시:

```md
# Team Engineering Rules
```

### 2.3 Skill 기반 로딩 — 작업 시점에만 로드

모든 규칙을 항상 컨텍스트에 넣지 않습니다. 필요한 작업 시점에만 로드:

```text
.claude/skills/coding-convention/SKILL.md
```

```md
---
name: coding-convention
description: 팀 코딩 컨벤션 검토
---

코드 수정 전:
1. docs/conventions/* 확인
2. 주변 유사 코드 확인
3. 새로운 패턴 생성 금지

작업 완료 후:
mvn spotless:check
mvn checkstyle:check
mvn test
```

효과:
- **토큰 절약**: 작업과 무관한 규칙은 컨텍스트에 안 들어옴
- **컨텍스트 오염 감소**: 관련 없는 가이드가 답변에 섞이지 않음
- **작업별 전문화**: coding-convention / analyze / analyze-cross-service 등 작업 단위별 특화 가능

### 2.4 왜 「서비스 중심」이 아니라 「유스케이스 중심」인가?

처음에는 서비스 폴더(`ordersubmit`, `ordercancel`, `ecouponService` 등) 안에 각각 `.claude/CLAUDE.md`를 두고 자동 로드되길 기대했습니다.

문제:
1. **하위 폴더 CLAUDE.md 자동 로드는 MSA에서 불안정** — 루트(`root/projectA`, `root/projectB`)에서 실행하면 특정 하위 디렉토리의 `.claude/CLAUDE.md`가 자동으로 붙는다는 보장이 없습니다.
2. **서비스 중심 분석은 다서비스 흐름을 못 잡는다** — `ecoupon` 분석은 주문 생성/주문 취소/결제/상품/e쿠폰/현금영수증/관리자 기능/MQ까지 다 얽힙니다. 폴더 단위로는 추적이 안 됩니다.

→ 분석 단위를 **유스케이스/기능 중심**으로 변경:
- 주문 / 주문취소 / 반품 / 교환 / e쿠폰 / 현금영수증 / 특정 상태 변경 / 특정 실패 전파 흐름

### 2.5 역할 분리

```text
CLAUDE.md  = 라우터 (얇게 유지)
docs/      = 지식 베이스 (architecture / usecases / policy)
SKILL.md   = 실행 플레이북 (analyze / analyze-cross-service)
```

### 2.7 flow / flow-deep 2단 문서 전략

복잡한 시스템에서 문서가 하나만 있으면:
- 너무 짧으면 실무에 부족
- 너무 길면 안 읽힘

그래서 2단 분리:

**`{case}-flow.md` (요약):**
- 처음 보는 사람이 5분 안에 큰 흐름을 이해
- 유스케이스 개요, 분석 범위, 대표 진입점, 대표 호출 체인, 서비스별 역할 요약, 핵심 상태 변경 지점, 동기/비동기 큰 흐름, 운영 핵심 포인트

**`{case}-flow-deep.md` (상세):**
- 실제 수정/장애분석/리팩토링 참고용
- 진입점 후보와 실제 운영 경로, 상세 호출 체인, 주요 분기, 상태 소유 서비스, 동기/비동기 경계, 실패 전파/재시도/멱등성/보상 처리, 운영/관리 기능 개입, 레거시 흔적, 코드상 리스크 포인트

### 2.8 analyze skill — 범용 분석 도구

도메인별로 `analyze-order`, `analyze-return`처럼 잘게 쪼개기 전에 **범용 analyze skill**을 둡니다.

분석 대상:
- 주문 / 주문취소 / 반품 / 교환 / e쿠폰 / 현금영수증
- 특정 API endpoint / 특정 상태값 변경 흐름 / 특정 장애·실패 전파 흐름
- 특정 MQ consumer / scheduler / batch / 관리자 기능 개입 여부

공통 분석 원칙:
- 실제 호출 흐름 기준으로 판단 (파일명/클래스명만 보고 추정 금지)
- 레거시 흔적과 현재 운영 경로 구분
- **「호출한다」와 「상태를 소유한다」 구분**
- 단순 조회/중계와 실제 상태 변경 구분
- 동기/비동기 구간 분리
- 문서와 코드가 다르면 단정하지 않고 **차이 기록**
- 애매하면 사용자에게 **반드시 질문**

### 2.9 핵심 효과

「Claude가 컨벤션·도메인을 기억해줄 것」이라는 환상을 버리고, **매 작업마다 필요한 docs가 Skill을 통해 자동으로 로드되어 동일한 컨벤션·동일한 분석 경로를 따라 작업하는** 구조를 만든 것이 핵심이었습니다. CLAUDE.md가 무거우면 토큰 낭비, 비워두면 컨벤션 미준수 — 그 사이를 **Skill 기반 선택적 로딩 + 유스케이스 중심 docs**로 해결했습니다.

> 차후 확장 포인트: Pre-commit Hook / CI Validation / Branch Protection을 통한 머지 단계 차단까지 도입하면, AI가 틀려도 시스템적으로 막히는 4단 차단 구조가 완성됩니다. (현재 미구현, 가이드 단계까지 적용)

## 어려웠던 점

### 1. 「AI가 운영DB를 직접 보면 안 된다」는 원칙을 팀에 설득

처음에는 「그냥 ReadOnly 계정 주면 되지 않냐」는 의견이 많았습니다. 하지만 AI가 만든 SQL은 사람의 의도와 다르게 동작할 수 있고(Full Scan, 잘못된 조인), 개인정보 컬럼이 그대로 LLM 컨텍스트로 들어가는 순간 외부 LLM의 캐시·로그에 남을 위험이 있습니다. → Context API + Tool Gateway + Audit 구조의 필요성을 사례 기반으로 정리해서 합의를 끌어냈습니다.

### 2. Context API를 「테이블 단위」로 만들 뻔한 함정

초기 설계 회의에서 「point-info API, order-info API, product-info API를 다 만들자」는 흐름이 있었습니다. 이렇게 가면 AI가 조인을 추론해야 하고, 운영 테이블 구조가 그대로 노출됩니다. → **업무 Context 단위**(`/context/checkout`)로 묶고, reasonCode로 의미를 코드화하는 방향으로 정정했습니다.

### 3. Claude Code가 컨벤션을 「기억해줄 것」이라는 환상

「CLAUDE.md에 컨벤션을 다 적어두면 Claude가 알아서 지킬 것」이라는 기대가 있었습니다. 실제로는:
- CLAUDE.md가 너무 두꺼우면 토큰 낭비
- 매번 다른 부분만 컨텍스트에 들어옴
- Claude가 컨벤션을 「잊은 듯한」 코드를 생성

→ 「AI의 기억에 의존하지 않고 docs·Skill 구조로 행동을 유도」하는 방향으로 전환. CLAUDE.md는 라우터로 얇게 두고, 세부 규칙은 docs/conventions에 두고, 작업 시점에 Skill을 통해 필요한 규칙만 로드되도록 설계했습니다.

### 4. 하위 폴더 CLAUDE.md 자동 로드의 불안정성

`projectA/src/ordersubmit/.claude/CLAUDE.md`, `projectA/src/ordercancel/.claude/CLAUDE.md` 같은 식으로 폴더별 상세 규칙을 두고 자동 로드되길 기대했지만, 루트에서 실행할 때 안정적으로 붙는다는 보장이 없습니다. → CLAUDE.md는 얇게 두고, **Skill 기반 명시적 로딩**으로 전환했습니다.

### 5. 서비스 중심 분석의 한계

`ecoupon` 분석을 「ecouponService 폴더」 기준으로 시도했더니, 실제 흐름은 주문 생성·주문 취소·결제·상품·관리자 기능·MQ까지 다 얽혀 있어서 폴더 단위 분석으로는 추적이 불가능했습니다. → **유스케이스 중심 분석 + analyze-cross-service 보조 skill** 도입.

- **운영 이슈 분석 속도 향상**: 정책·코드·운영 데이터를 사람이 매번 직접 연결(Context Stitching)하던 작업을 AI가 일관된 구조에서 수행 가능

- **추정 기반 분석 → 운영 경로 기반 분석으로 전환**: 코드만 보고 「아마 이럴 것」이라고 단정하는 분석에서, 정책·문서·코드 충돌 시 질문을 강제하는 분석으로 변화
