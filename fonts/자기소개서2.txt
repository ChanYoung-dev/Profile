제가 수행한 프로젝트 중 기술적으로 가장 도전적이었던 경험은 주문 고도화 프로젝트에서 테스트 코드를 도입한 경험입니다. 특히 주문 도메인은 기존에 테스트 코드가 존재하지 않는 레거시 영역이었으며, 동시에 MSA 구조로 운영되고 있어 테스트 전략 수립이 큰 과제였습니다.

주문 도메인은 배송, 결제, 쿠폰, 포인트, 상품 등 여러 도메인이 복잡하게 얽혀 있었고, 복합 결제 주문, 부분 취소, 수량 기반 결제, 연마감 이후 결제 취소 등 다양한 시나리오를 포함하고 있었습니다. 이로 인해 특정 기능을 일부 수정하거나 정책을 추가하더라도 사이드 이펙트가 발생했으며, 변경 시마다 광범위한 수동 검증이 필요해 개발 효율성을 크게 낮추었습니다.

이를 해결하기 위해 테스트 코드 도입을 결정했지만, MSA 환경에서의 테스트는 또 다른 난관이었습니다. 예를 들어 주문 API에 대한 통합 테스트를 수행하기 위해서는 상품 정보가 필수였는데, 이 상품 데이터가 어느 경로를 통해 제공되어야 하는지부터가 문제였습니다. 개발기 상품 API를 호출할 것인지, 로컬에 상품 API를 띄워 연동할 것인지, 혹은 개발 DB를 직접 사용하는 것이 맞는지에 대한 판단이 필요했습니다. 더불어 서비스 간 트랜잭션이 분리된 MSA 구조 특성상, 분산 트랜잭션 흐름을 테스트 환경에서 어떻게 검증할 것인지 역시 쉽지 않은 문제였습니다.

또 하나의 어려움은 통합 테스트 수행 시 Persistence Layer를 어떻게 다룰 것인가에 대한 고민이었습니다. 실제 운영과 유사한 검증을 위해서는 데이터베이스를 포함한 테스트가 필요했지만, 테스트 환경의 구축 비용과 안정성 또한 고려해야 했습니다. 이에 저는 통합 테스트 환경을 설계하는 과정에서 Mock 기반 테스트, Alpha DB, 테스트 전용 DB, In-Memory DB, TestContainer 등 다양한 대안을 검토했습니다.

이러한 고민 끝에 저는 통합 테스트의 목적을 명확히 정의하는 것이 중요하다고 판단했습니다. 모든 의존 서비스를 로컬 환경에 띄워 실제 운영 환경과 동일하게 검증하는 방식은 이상적일 수 있으나, 테스트 환경 구축과 유지에 과도한 시간이 소요되어 실질적인 개발 생산성을 떨어뜨릴 수 있었습니다. 따라서 테스트의 범위와 깊이에 대한 현실적인 trade-off가 필요하다고 보았습니다.

그 결과, 정합성과 데이터 일관성이 중요한 핵심 주문 시나리오에 대해서는 TestContainer 기반의 통합 테스트를 선택했습니다. 특히 주문 도메인은 복합 결제, 부분 취소, 연마감 이후 취소 등 데이터 정합성이 깨질 경우 장애로 직결되는 영역이었기 때문에, In-Memory DB와 같은 대안보다는 실제 운영 DB와 동일한 Oracle 환경에서 검증하는 것이 필요하다고 판단했습니다. TestContainer를 활용함으로써 테스트 실행 시점마다 독립적인 데이터베이스 환경을 구성할 수 있었고, 운영과 유사한 SQL 동작과 트랜잭션 흐름을 검증할 수 있었습니다.

반면, 외부시스템이나 주문 흐름상 영향도가 상대적으로 낮은 영역에 대해서는 Mocking을 활용한 테스트 전략을 적용했습니다. 외부 시스템까지 모두 포함한 통합 테스트를 구성할 경우 테스트 시간이 과도하게 길어지고, 장애 원인 또한 외부 요인에 의해 불명확해질 수 있다고 판단했기 때문입니다. 이에 따라 핵심 도메인 로직과 직접적인 연관성이 낮은 영역은 Mock을 통해 동작만 검증하고, 주문 도메인의 정합성과 상태 변화가 중요한 구간에 집중했습니다.

이러한 경험을 통해 저는 테스트 코드 도입은 단순한 검증 수단이 아니라, 좋은 설계로 이어지는 출발점이라는 것을 배웠습니다. 테스트 가능한 구조를 만들기 위해 객체의 책임을 분리하고 의존성을 낮추는 과정에서 자연스럽게 SOLID 원칙을 따르는 설계로 이어졌고, 이는 변경에 강한 아키텍처를 구축하는 기반이 되었습니다. 그 결과 정책 변경이나 기능 추가 시 발생하던 사이드 이펙트가 눈에 띄게 감소했으며, 수동 검증에 소요되던 시간이 약 70% 이상 단축시키는 결과를 얻었습니다.


동기



저는 강한 정합성이 요구되고 복잡한 관계를 갖는 도메인을 안정적으로 운영해온 Back-End 개발자입니다. 주문·결제·배송 도메인을 담당하며 데이터 불일치, 중복 처리, 장애 전파와 같은 실제 운영 이슈를 직접 경험하였고, 이러한 장애에 대해서는 단순 복구에 그치지 않고 근본 원인 분석과 정책 재정립을 바탕으로 구조 개선과 재발 방지에 집중해왔습니다. 이 과정에서 비동기 처리와 메시지 기반 설계, 테스트 코드 도입 등을 통해 시스템 전반의 안정성을 높였으며, 운영 신뢰도 또한 함께 개선할 수 있었습니다. 또한 XSS 대응과 같은 시큐어 코딩을 서비스 전반에 일관되게 적용함으로써, 보안 취약점으로 인한 잠재적 리스크를 줄이고 안정적인 운영 환경을 구축했습니다.

귀사에서는 이러한 경험을 바탕으로 정합성과 안정성이 중요한 핵심 백엔드 시스템을 더욱 신뢰할 수 있는 구조로 발전시키는 데 기여하고 싶습니다. 장애에 강한 설계와 운영 경험을 통해 서비스 품질을 지속적으로 끌어올리는 역할을 수행할 수 있다고 생각합니다. 아울러 MSA 환경에서 쌓아온 경험을 확장해, 더 큰 규모와 복잡도를 가진 시스템을 직접 다루며 한 단계 더 성장하는 Back-End 개발자가 되고자 지원하게 되었습니다.
